## 一、英文候选里的非单词碎片（已修）

### 根因（实证，不是推断）

wordfreq 的 large 表是**语料统计**，不是词典：除真词外还带脱掉撇号的缩合
（`dont`/`didnt`）、社媒拼写（`lol`/`wtf`）、被切碎的词头（`gra`/`lun`/`bri`/
`holi`/`bre`）、两三个字母的 URL 残渣（`ve`/`im`/`gc`/`aj`/`zz`）。

中文模式下打的是**拼音缩写，占同一个键盘区**。`ve` 这种输入连中文候选都没有：

```
dump(ve) → ["ve[en]4.56"]        ← 唯一候选，band 落到 EnglishFirst 排第一
```

于是**按空格就把 `ve` 这个不是单词的字符串上屏了**——正是用户描述的现象。

### 修法

新增 `scripts/english/quality.py`，构建期过滤（`--reference` 参考词表）：

| 顺序 | 规则 | 挡住的 | 救回的 |
|---|---|---|---|
| 1 | 人工清单（`--entries`/`--overrides`）永远保留 | — | `python`/`api`/`css` |
| 2 | 精确命中参考词表 | — | `hello`/`docker` |
| 3 | ≤2 字母走白名单（`SHORT_WORDS` 封闭集合） | `ve`/`im`/`gc`/`ll` | `a`/`i`/`am`/`ok` |
| 4 | 去词尾（含**双写辅音**）后词干命中 | — | `colors`/`centers`/`running` |
| 5 | `zipf_centi >= 400` | — | `math`/`lol`/`google` |
| 6 | 其余丢弃 | `gra`(272)/`lun`(267)/`bri`(286) | — |

**不给 `--reference` 时是恒等变换**（旧产物逐字节不变，向后兼容）。

### 踩过的两个坑（已在测试里钉住）

1. **hunspell 的 `/FLAGS` 必须先剥**：`github/SM` 过不了「纯字母」检查，不剥的话
   整份 `.dic` 里带标志的词（绝大多数）被当无效行丢掉，参考表从 **76 226 缩到
   约 15 789**，过滤随之过激——`github`/`center` 都被误删。修好后 `github` ✓。
2. **`protected` 必须是键集合**：`set(overrides)` 得到的是 namedtuple 集合，
   包含判断恒为假，人工清单形同虚设（`kubernetes`/`chatgpt` 被静默删掉）。

### 实测

| | 修前 | 修后 |
|---|---|---|
| 词数 / 前缀 | 50 002 / 116 134 | **42 770 / 103 819** |
| 体积 | 4.46 MB | **3.94 MB** |
| 过滤原因 | — | reference 41 461 · stem 675 · frequent 70 · short 595 · **junk 7 219** |

`overrides.tsv` 扩到 64 行（技术词与专名——参考词表对这类覆盖很差，
靠频率规则会被误删）：`api`/`css`/`sql`/`npm`/`nginx`/`redis`/`sqlite`/
`mongodb`/`kubectl`/`tls`/`vpn`/`graphql`/`oauth`/`jwt`/… 键只能是纯 ASCII
字母，`k8s` 这类带数字的写法在格式里表达不了。

**候选实测**：

```
ve   → ["ve[echo]"]                     ← 只剩原文回声，没有英文单词
ll   → 无英文候选（纯中文）
gra  → grand / grade / 感染 / grab …    ← 修前全是中文
holi → holiday / holidays / …           ← 修前全是中文
bre  → break / bread / …                ← 修前全是中文
api  → API / apis / …                   ← overrides 生效
kubernetes → Kubernetes / …             ← overrides 生效
```

**唯一残留**：`cit`（SymSpell 与 hunspell **都**收录，freq 289）仍会作为
精确命中排第一。它不属于「拼装出的垃圾」，是两份词表的共同判断，保留。

## 二、补全未达标（修到 66.7%，其余缺口已定量拆分）

### 修的部分：`EnglishFirst` 模板自相矛盾

原模板 `E E Z E Z Z Z Z Z`（`docs/english-input/02-engine.md` 第 9 节）：第 3 槽
被中文占掉，于是**英文通道的第 3 名在混排里恒为第 4 名**。这与档名、与决策表
里「`good_en` 且 `strong_completion` ⇒ EnglishFirst」（这条规则存在的**唯一
目的**就是让补全进首屏）直接冲突，给「补全 Top-3」压了一条结构性天花板。

改为 `E E E Z Z Z Z Z Z`（英文前三个槽位）。中文候选一个不丢——模板只调次序，
首个中文位从第 3 槽挪到第 4 槽。

**试过又回退**：`Mixed` 也改成 `Z E E Z` 能再多 3 行（66.7% → 70.0%），但
那偏离了该档「交替」的档义（它用于意图不明，交替是对冲），收益不值这个代价，
已回退。

### 剩余缺口（38 条失败 = 24 条补全 + 其余）

| 类别 | 条数 | 性质 |
|---|---:|---|
| 目标在纯静态词频下就排第 5 名以后 | **11** | **标注本身要求打败词频先验**，不是实现缺陷 |
| `strong_zh` 命中（输入本身是合法中文拼音：`ban`/`che`/`lun`） | 多数 | **中文保护按设计生效**，改它就是拆掉验收的另一半 |
| `Mixed` 模板英文第 2 名落到第 4 位 | ~9 | 交替档的设计取舍（上节已试并回退） |
| 目标不在英文通道内部 Top-3 | 21 | 英文通道内部 Top-3 = 69/90 |

**结论：`补全 Top-3 ≥ 90%` 与 `中文保护` 在短前缀上互斥。** 3 个字母的英文前缀
里有一大批本身就是合法中文拼音（`ban`/`che`/`lun`/`yea`…），中文保护要求这些
输入中文优先，补全 Top-3 又要求英文补全进前三。要同时满足 90% 只能弱化中文保护，
而中文保护是规格里另一条硬门槛——**这需要用户拍板，我没有自行取舍**。

### 顺手修掉的标注自相矛盾（1 条）

`acc-c001`：`input=teach, target=training`——**`training` 根本不是 `teach` 的前缀**，
却被标注成「补全」。已改为 `teaching`（真正的补全）。全量扫过：180 条英文 query
行里只有这 1 条违反「目标必须是输入的前缀」。

`tune-a004`：`target=wo`——`wo` 是**拼音音节**（我/握/窝）不是英文单词，质量过滤
之后它不在英文词表里了。与之前 `in/is/it/us` 同类修正，已改为 `word`。

## 三、卡顿（定位完成，**未动核心排序**）

### 用户的感受被数据证实

新增 `crates/xwx_engine/examples/latency_probe.rs`（按真实会话逐键计时，
release + 真实数据）。**先确认不是构建类型问题**：已安装的
`/home/youngwen/.local/bin/xwx_ime` 与本地 release 产物**字节数完全相同**
（12 965 800），不是 debug 构建；`/usr/bin/time -v` 显示 **0 次 major page
fault**，也不是 IO/页缓存。

**热态逐输入（最后一次按键，30 轮 p50）**：

| 输入形态 | 例子 | p50 | 候选 |
|---|---|---:|---:|
| 双字母全拼 | `ni` | 0.052ms | 24 |
| 五字母全拼 | `nihao` | 0.147ms | 27 |
| 九字母全拼 | `jintiantian` | 0.704ms | 170 |
| 双字母简拼 | `nh` | 1.363ms | 169 |
| 六字母简拼 | `nhsytx` | **6.262ms** | 87 |
| 长简拼 | `wmjtwmyqbj` | **8.999ms**（p95 14.9，max 18.3） | 132 |
| 词库无解 | `zzzzz` | **5.344ms** | 45 |

**全拼完全正常（≤0.7ms），慢的全是简拼与无解输入。**

### 热点（用项目自带的 `XWX_TRACE` 分期计时，`perf` 被内核
`perf_event_paranoid` 拒绝）

```
zzzzz      建精确格 0.004ms | 建简拼格 2.115ms | 建纠正格 1.159ms
wmjtwmyqbj 建精确格 0.005ms | 建简拼格 2.860ms | 建纠正格 1.887ms
nihao      建精确格 0.090ms | （不建简拼格、不建纠正格）
```

再往里拆：`建简拼格` 里「整串匹配」三个查询合计只占 0.55ms，**BFS 占 2.27ms
而只走了 10 步**（≈0.23ms/步）。热点是
`engine/lattice/build.rs::build_abbrev_lattice` 的 `collect_chain_edges` DFS，
预算是 `MAX_ABBREV_CHAINS_PER_START = 2048`（起点 0 一次吃光）。

`zzzzz` 这种**词库完全无解**的输入仍要花 3.3ms 走完简拼格与纠正格，是纯浪费；
但降预算这条路上有既有注释明确记录过「降预算会饿掉整句读法」（实测
`womenjinxtianqugongyuan` 从「我们今天 #1」退回「我们 #1」），所以**不能盲调**。

### 为什么本轮没修

修它要动 `build_abbrev_lattice`/`collect_chain_edges`——中文排序的核心路径，
而这条路径有该引擎最密集的调参历史（预算、去重、层序破例都踩过坑）。
正确做法是**带对拍基准的独立一轮**：先给 `eval_rank` 五套语料建立「简拼质量
基线」（现有基线只覆盖排序结果，不覆盖预算余量），再逐项试优化，每步都比对
中文排序是否逐字不变。在已经改了英文词典与混排模板的这一轮里顺手动它，
是把两个独立风险叠在一起。

**给用户的可用缓解**：简拼慢只影响连续辅音缩写；全拼（每键 ≤0.7ms）不受影响。
