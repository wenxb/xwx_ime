## 1. 定过又推翻的判断（别再走一遍）

### ① 「A 和 B 必须一起做，否则返工」——**错的**
我最初认为 Block A（候选管线）和 Block B（输入缓冲）都要动 `lookup_candidates`，
分两次做会返工。**重读代码后不成立**：A 消费的是「格 + 后向 DP」，
B 改变的是「格里有哪些边」和「输入串形状」，B 后做不会迫使 A 重写。
真正强耦合的只在 **B 内部**（B1/B2/B3 共享输入缓冲与切分层）。

### ② 「简拼要给 SYLLABLES 加单字母音节」——**绕开了**
一度以为简拼必须让 `zgr` 能被切成 `['z','g','r']`，就得往
`segmenter.rs:SYLLABLES` 加单字母音节——而那里的注释明确说了不能加
（DP 会产生大量无意义切分）。
**最终方案绕过了这个两难**：`lookup_abbrev`/`lookup_mixed` 返回的词
**本来就覆盖整个输入串**（用户打前缀、拿到整词），所以它们是整串候选，
直接合并进候选列表即可，**根本不进 lattice**。

### ③ 「调排序那 39 个词收益最快」——**夸大了一个数量级**
按字/词拆开后：33 个是单字同音字排序差异（rime-ice 与 luna 的词频数据差别，
**去对齐 librime 不是目标**），多字词只有 6 个，其中 5 个是生僻词
（明体/钟鼓/中古/公族/终古），**真正常用又排得离谱的只有「西安」（第 18 名）**。
教训已写进记忆「判据要在测量前钉死」。

### ④ 「音节表要构建期写进 abbrev.bin（v2 格式）」——**不必要**
实测 `segmenter.rs` 的静态 `SYLLABLES` 有 410 个，词库实际用到 412 个，
差集只有 `fiao`/`tei`，反向差 0。**直接用静态表**即可，
不用引入 v2 文件格式。详见 `PLAN.md` 第三节。

### ⑤ 「按未解释输入字母数当硬首键」——**规则本身有缺陷，已推翻**
为了让混合简拼的目标词露面，我定过一条规则：排序首键 = 未解释输入字母数
（候选拼音覆盖不到的字母数）。混合简拼确实修好了（中国人 22 → 1），
**但全拼第一页被生僻组合词淹了**：`beijing` 的「被/备/北」被
「被禁锢/悲寂/背脊」顶掉，`diannao` 冒出「狄安娜/蒂安娜」，
`jinan` 冒出「进啊」这种不成词的东西。

**关键洞察：病根在度量，不在系数。** 我的第一反应是「把硬首键改成罚分、
调系数」，执行者实测 0.5/0.75/1.0/1.5/2.0 五个值，发现「被禁锢」在**任何**
系数下都稳居第 5——因为 `bei-jin-gu` 的拼音长度**确实**等于输入长度，
裸覆盖度看不出它和「被」的区别。

定稿是换度量：看**剩下的字母还能不能精确切分成音节**（`u_min` 分桶）。
「中国人」之于 `zhongguor` 剩下的能切完 → 0 桶；「被禁锢」把 `jing` 拆成
`jin`+`gu` → 沉底。换了度量之后，A（全拼第一页）和 B（简拼露面）立刻同解。

> **这条是我的判断失误**：执行者按我写的规则精确实现了，也报告了
> 「单字想上屏要多翻一点，这是本规则的刻意取舍」——是我没预见到
> 「0 键生僻组合词淹没高频单字」的规模就签了字。

### ⑥ 「西安第 18 名是 A3 后向 DP 近似丢了 bigram」——**归因是错的**
这条错误归因在 `PLAN.md` 里挂了很久。实测推翻：`xian` 本身是合法音节，
「西安」与「先/现/线」**都覆盖整串**、后缀补全分**都是 0**，
A3 的后向 DP 对它们不产生任何区分。

真因是 `wanxiang.rs` 的 `score_word()` 空上下文早退返回
`floor_log10()`（≈ -11.6058，**与候选词无关的常数**），于是
**空上下文时排序 100% 由词频决定，LM 完全不参与**。
这个事实的影响面远大于「西安」——**输入法里绝大多数上屏都从空上下文开始，
也就是说每次输入的第一个词都是纯词频排序**。

旁证：`nimen`→你们 第 1、`jinan` 前 6 全是双字词，
说明 bigram 缺失根本不足以让双字词沉底。真正的分界是
**「整串是否恰好是一个合法单音节」**——是的话，覆盖整串的高频单字边
会和多字词同槽同补全（都是 0），退化成纯比词频。

### ⑦ 「空上下文查 unigram 就能修好」——**结构性走不通，别再试**
详细反例见 `PLAN.md` 第四节。一句话：**万象 gram 的值不跨键长可比**
——单字条目根本不存在（窗口模型最小 2 字），长命中键的 ln 随键长单调涨，
所以「狄安娜」(13.81) 会骑到「西安」(11.21) 头上。
实测四个参数版本全部在既有哨兵上出血，已完整回退。

### ⑧ 「A1 已经修完了」——**只修了一半**
Block A 的 A1「候选只能起始于位置 0」当初**只修了格（lattice）路径**，
`fallback_candidates` 里同样的 `for syllable in seg` 漏了。
后果是 `zhongguor` 前 20 名有 13 个只覆盖非起始音节的字。
**混合简拼打不出字，根子在这**——绕了两轮（配额、残余字母联想）才挖到。
那两轮的改动本身没错、也都保留至今，但都没打在要害上。

### ⑨ 「这个功能已经做完了」——**文档打勾 ≠ 二进制里有**（2026-10-01）

一次外部审查发现**三处**同一类病：测试全绿、文档打勾、用户却用不到或反受害。
这是本项目最该警惕的一类缺陷——**它不会让任何测试变红**。

**① 模糊拼音在生产里是死代码。**
`fuzzy_enabled` 只在 `lib.rs` 定义 / 初始化 false / 一处分发，
**其余全部在测试里**（测试自己置 true）。`main.rs` 从不设置它，
没有配置入口——而 `README.md` 早已打勾「模糊拼音 ✅」。

> **教训：`grep` 一个配置字段的「赋值点」，比读它的测试更能判断功能是否可达。**
> 测试里绿的是「能力」，不是「接线」。凡有开关的字段，都要 grep
> 进程入口里**有没有人真的打开它**。
> 已接线成 `XWX_FUZZY`（默认关闭，实测依据见 `PLAN.md` 2026-10-01 节）。

**② 造词把「连续打字」粘成句子词条。** 证据在真实用户数据里：
`~/.local/share/xwx/user_bigram.txt` 躺着 `当前主线以及已经完了是吧进度`
这种 11 字句子。根因是判据只数片段个数，不管片段**是什么**。

> **教训：用户数据文件是最诚实的需求文档。** 我们有一堆造词测试
> （单次完整词不重复造、跨标点不造、跨焦点不造）——全都绿，
> 但没有一条覆盖「用户连续正常打字」这个最高频场景。
> **测试覆盖的是我们想到的场景，用户数据反映的是真实发生的场景。**

**③ README 落后 PLAN 一个数量级。** 旧 TODO 六条里五条早做完了却挂着
未打勾；模糊拼音反过来——打着 `[x]` 但生产里无法启用。对外表述**又少又错**。

> **教训：能力 / 文档 / 生产三者要定期对账。** 判据会腐烂（第 3 节），
> 文档也会——而且更隐蔽，因为它不参与任何自动化检查。

### ⑩ 「空上下文排序 100% 由词频决定」——**对通用层成立，对用户层不成立**（2026-10-01）

`PLAN.md` 第四节那句结论需要收窄。实测（`examples/lm_ctx_probe.rs`）：
空上下文下万象对**任何**词返回同一个常数 `-11.605767`
（「西安/先/闲/狄安娜/中国/的/**龘**」七词逐位相同，连词库里不存在的字都一样）。
**但**生产进程挂了用户层，`UserLmSnapshot::log10_prob` 在无 `prev` 时
回落 unigram 计数——**用户用过的词在句首是可区分的**。

> **教训：「LM 不参与」这类结论要先问「哪一个 LM」。**
> 引擎是 `LmStore` 枚举聚合（Bigram / Wanxiang / Mixed），
> 只看 `wanxiang.rs` 就下结论会漏掉用户层。
> 这同时划清了「空上下文 unigram backoff 被否决」的**边界**：
> 被否决的是**通用 gram**（值不跨键长可比），
> 用户层 unigram 是可比的自然数——将来再动空上下文，别把它一起砍了。

### ⑪ 移植一个组件前，先确认它挂在**哪条链**上（2026-10-01）

`MAX_COIN_CHARS` 的原注释称它「对应 librime `unity_table_encoder` 的长度上限」。
实读 `/usr/include/rime/gear/unity_table_encoder.h` 后确认**溯源是错的**：
`UnityTableEncoder` 是 **`table_translator`（码表）**的组件，
而拼音走的是 **`script_translator`**——后者根本没有 encoder
（这一点 `gear-audit.md` 第 3 节其实早就写明了）。

> **教训：`gear-audit.md` 这类清单要连「挂在哪个 translator 下」一起读。**
> librime 有多个 translator（table / script / reverse_lookup…），
> 组件清单是**按 translator 分组**的。只对着组件名找对应关系，
> 就会把码表的特性搬到拼音引擎上。
> 24 这个数值本身仍合理（覆盖人名/诗句），保留；但理由要换掉。

### ⑫ 测试设施自己会撒谎：一次集成层「全绿」的六重假象（2026-10-01）

根 `tests/` 的 D-Bus 集成层交付时声称「7 passed」，实际是**大部分红、
部分永久挂起**（一次跑了 15 分钟不返回，还漏了 4 个孤儿引擎 + 4 个孤儿
bus）。逐条挖出**六个缺陷，全部在测试设施里**，引擎侧无罪。这六条是同一
类病的六个面：**测试没在测它声称测的东西**。

1. **信号 100% 被静默丢弃**。监控线程用
   `Body::deserialize::<OwnedValue>()`；每个 IBus 信号体都是**多字段结构**
   （`UpdatePreeditText` = `(vubu)`），`OwnedValue` 只接受单值 → 反序列化必失败
   → `continue` 丢掉 → 所有断言报 `已见: []`。**测试红了却指向引擎，
   而引擎一直在正确发信号。** 改 `deserialize::<Structure>()`。
   > 教训：**`let Ok(..) = ... else { continue }` 是最危险的写法**——
   > 它把「解析失败」和「没有信号」变成同一种可观测结果。凡是静默 `continue`
   > 都要能报数。

2. **变体没拆**。IBus 把对象藏在 variant 里：体是 `(v u b u)`，第 0 个字段
   是 `v` 包着 `IBusText`。访问器却按「体就是 IBusText」读第 2 个字段
   → 读到 `Bool(true)` → 文本恒为 `None`。拆包后，**测试原本断言的
   `(sa{sv}sv)` / `(sa{sv}uubbiavav)` 恰好是内层签名**——断言其实是对的，
   错的是解码层。

3. **空体信号被丢**。`HidePreeditText()` / `HideLookupTable()` 的体是空，
   结构反序列化失败 → 又被 `continue` 丢掉 →「Esc 后必须发 Hide」永远红。

4. **方法调用没有超时**。`zbus` 阻塞式 `call_method` 自身**无超时**：引擎一旦
   不应答，调用就停在 `epoll_wait(-1)`，测试线程永不返回，整个套件挂死
   （strace 抓到：主线程在 `futex` join 一个卡死的测试线程，那个线程在
   `epoll_wait(..., -1)`）。改成 worker 线程 + `recv_timeout` 后，
   **挂起变成一条点名方法的失败**——套件从「永不结束」变成 13 秒跑完。

5. **监控器是懒创建的**。`ensure_monitor()` 原本只在第一次 `settle`/`drain`
   时调用。测试若**先打字、后 settle**，信号在 match rule 注册前就发完了
   → 收到空批次 → 却报「没有候选窗」。改为 `start_engine` 里**先监听再放行**。

6. **静默期太短的假等待**。多处 `settle(60ms, ..)` 靠「安静 60ms」判定收集
   结束——负载下信号晚到就被截断。改成 `wait_signal("UpdateLookupTable", ..)`
   **等指定的那一个**。注意 `clear_backlog()` **同时会 drain 信号通道**，
   所以它必须**在动作之前**调用；放在动作之后会把你正要等的信号冲掉。

> **总教训**：一个「全绿」的测试套件，只有在**它有能力变红**时才值钱。
> 这六条里有五条的表现是**红/挂**，但都指向了错误的方向（引擎），
> 真正的问题是断言根本没接上被观测的信号。**先证明测试能看到东西
> （`已见: [...]` 非空），再谈它断言得对不对。**

### ⑬ 引擎真 bug：先占名字、后挂对象（2026-10-01）

集成层唯一挖到的**引擎**缺陷，而且是对的：`src/main.rs` 原本先
`conn.request_name(ENGINE_SERVICE)`，**之后**才
`object_server().at(FACTORY_PATH/ENGINE_PATH)`。于是存在一个窗口：
**名字已可见、路径还没人应答**——此刻到达的方法调用永远不会返回。
实测形态：`FocusOut` 10s 无应答，而引擎进程 `/proc` 状态是 `S`（活着）、
日志干净（启动完成），即**活着但不分发**。

修法：**先 `at()` 挂对象，再 `request_name`**——「名字可见」就必须
「即可服务」。这是 D-Bus 的标准做法，不是绕行。

> 教训：**`request_name` 是「发布」，发布之前必须先能履约。**
> 这类窗口在单测里永远看不见（单测直接调库函数，不过总线），
> 只有真正跨 D-Bus 边界的测试才抓得到——这正是集成层存在的理由。
> 测试侧同时加了 `Peer.Ping` 就绪探针（`zbus` 自己应答，
> 比 `GetNameOwner` 更能证明「对象已在分发」），两层保险。

### ⑭ 用户层给「没学过」的词发**绝对**中性分 = 学习反而降权（2026-10-02）

用户报「纯简拼 `ky` 里『可以』不在前面」（`可以` 词频 505814，是 `ky` 全桶
最高）。根因**不在简拼算法**，在 `MixedLM::score`：用户层对没有证据的词
发一个**绝对**中性分（`NEUTRAL_LOG_PROB = -1.0`），而用户层自己的概率是按
**用户语料规模**归一化的——真实 `~/.local/share/xwx/user_bigram.txt`
（Σc+vocab ≈ 175）下，计数 1 ≈ ‑1.94、计数 3 ≈ ‑1.64，**全在中性分之下**。
于是学过的「可以」被压到第 **11** 名，从没学过的「跨越/可用」白拿 ‑1.15。

> **教训：跨模型混合时，绝不能用一个绝对常数当「不表态」票。**
> 两层量纲不同（一个按通用语料，一个按用户自己的几十条计数），
> 这个常数落在哪一侧完全取决于用户打了多少字——用户用得越多，
> 结论越会翻转。正确口径是 **backoff**：没证据 ⇒ 原样输出通用层分
> （没学过的词逐位不变）；有证据 ⇒ 概率域插值，且结果
> `.max(base)`——**学习永不降权**（计数只有正证据，负证据是
> Ctrl+Delete 的屏蔽表）。
> 附带挖出一条同类：`coin_entry` 只 `add_entry` 不 `learn`，
> 自造词「查得到但排不上」（旧断言是**靠中性分**偶然排到第 1 的），
> 已补上计数——`user_lm.rs` 的 `entries` 注释本来就写着
> 「召回与打分两条通道一体」。

### ⑮ 跨模型混合：绝对概率常数会随语料规模漂移，**计数才是不变量**（2026-10-02）

用户追问「选错一次会不会一直错下去」时查出的三条实测事实：

1. **一次误选永久置顶**：`xian` 误选「闲」1 次 → 第 1（初始第 10）；随后连
   选对「先」3 次 →「先」回第 1，但「闲」稳居第 2，只能 Ctrl+Delete 清。
2. **个人加分随语料规模衰减**：同一句「学 1 次目标词」，往用户表里灌
   0/200/2000/10000 条无关语料后，加分 +11.45 → +9.15 → +8.15 → **+7.45**
   ——重度用户的个人化比新用户弱 4 个数量级。
3. **断崖而非梯度**：学过 vs 没学过差 ~9 个数量级，而学 1 次 vs 3 次只差 0.2。

> **教训：跨层混合时，两个量纲「可不可比」看分母，不看形式。**
> 用户层概率的分母是**用户自己的语料规模**，通用层是全民语料——把它们送进
> 同一个 logsumexp 做插值，等于假设两者可比，而这个假设会随用户打字量漂移
> （第 2 条）。可用的不变量是**计数**：它不依赖任何分母，换算出多少加分由
> 单一常数 [`USER_COUNT_GAIN_R`](../crates/xwx_engine/src/lm.rs) 决定。
> 改后的口径 `score = base + log10(1 + c·R)` 同时给出三条性质：无证据不动
> 通用层（c=0 ⇒ +0，逐位相同）、学习永不降权（加分 ≥ 0）、与语料规模无关
> （由 `mixed_boost_independent_of_corpus_size` 钉住）。
>
> 附带一条**语义反转**：Ctrl+Delete 过去刻意**不动**计数（理由「删候选 ≠
> 抹掉频次」），现在改成**连计数一起清**。原因是屏蔽键是 `(拼音, 词)` 而计数
> 按**词**记——只屏蔽的话，同一个词在别的拼音路径上照样带着计数被加分
> （多音字串味），用户看到「删了它，换个打法又冒出来还更靠前」。计数就是
> 排名的燃料，燃料不清等于没删。
>
> **标定方法（可复用）**：判据先钉死，再 sweep。先测候选分差只有两档
> ——同类词 vs 词 **0.002~3.70**，「逐字拆解 vs 整词」**10.1~14.7**——再拿
> `R ∈ {10,30,100,300,1000}` 扫「误选 #2/#5/#10 一次后落第几」，取
> **R=1000**（一次 +3.0 覆盖全部同类竞争；结构墙要 5×10¹⁰ 次才翻得过去）。

### ⑯ 「够了就停」= 隐式排序：收集期的早停是拿探索顺序当质量（2026-10-02）

`meiy` 打不出「没有」——**不是排序问题，是根本没召回**。DFS 收集期「收满
500 条就停」，而这 500 条按**探索顺序**先到先得（`mei y*` 下几百个 key，
`mei you` 还没轮到名额已被 `mei yi*` 占满）；**截断发生在排序之前**，
所以「按词频取前 N」根本没有机会生效。铁证：列表第 1 名「每一个」词频
500354，缺席的「没有」是 **504685**。

> **教训一：任何「够了就停」都是隐式排序**——它用探索顺序（= 代码结构、
> 字节序、循环次序）替代了打分。质量决策只能发生在**排序之后**。
>
> **教训二：成本问题先打桩量清「钱花在哪」，别猜。** 我先猜是「收词条太多」，
> 加了每 key 额度，实测 4/8/32 **毫无差别**（都是 3.8ms）；打桩才知道真正的
> 成本是 **DFS 探索本身**（20_000 步预算 × 每步一次二分迭代 ≈ 3.8ms）。
> 猜错方向会白改一轮。
>
> **修法与成本三件套**（判据先钉死再标定）：
> 1. 收集期不做决策 + 排序后 `truncate(500)` 按词频截断；
> 2. **探索上界** `MAX_MIXED_COLLECT = 8 × 500`：取消上界 → `zhongg`
>    0.343ms → 4.13ms（破 5ms 门槛）；上界 4000 → **2.80ms**；
> 3. **整 key 跳过**（精确分支界限）：词块内 freq 降序 ⇒ 「该 key 最高词频
>    < 收集池第 N 名的下界」就整 key 跳，一条都进不了最终列表。前提
>    「组内 freq 降序」经抽样验证（含「一」130 条）。
> 4. 索引预算 `MAX_MIXED_DFS_STEPS` **不动**——实测收紧到 6000 会把
>    `nhao` 的 14 条召回砍到 4 条：**用召回换速度是亏的**。
>
> **教训三：回归锉会锉住「假象」。** `mixed_abbrev_targets_are_visible` 里
> 「`nih`→你好 ≤ 2」是按**当时不完整的召回列表**标定的：新召回补进来的
> 「你会」(-15.836)/「你回」(-15.878) 词频本来就高于「你好」(-15.967)。
> 修好召回后它落到第 4。按项目规矩**逐条说明后**把上限改成 4（旧列表里的
> 你还/你和/你很 一条没掉，不是排序退化）。

### ⑰ 「整串是合法全拼」≠「用户打完了」；新能力会让旧断言假失败（2026-10-02）

T2（末尾半音节）踩到三件事：

> **一、同一个「末尾半个音节」有两种形态，必须都覆盖。**
> 尾巴不构成音节（`zho`→zhong）走 DFS 那条路；尾巴**碰巧是合法音节**
> （`niha` 的 `ha`、`beijin` 的 `jin`）会被判成「整串合法全拼」走精确匹配。
> 只在 DFS 那一条路上加半音节读法 → `niha`/`beijin`/`meiyo` **全漏**。
> 教训：**给查询加一种「读法」时，先数清入口有几条，读法要对每条都生效**
> ——所以两条路的结果要并进**同一个收集池**。
>
> **二、按能力切分，别把相邻能力顺手做进去。** 整串是全拼时，「`p = 0`」
> 的含义会从「末尾半截」变成**「音节前缀补全」**（`xian` → 整个 `xiang*`
> 区间）：那是另一个能力，实测端到端 3.10ms → **7.63ms**、候选列表从 100
> 条级别涨到满额。用「整串是否合法全拼」把两者切开后，四个目标形态一个不丢，
> 延迟回到 3.78ms。**范围边界要用测量来定，不要用直觉。**
>
> **三、测试会编码「旧能力的边界」，新能力会让它假失败。** 两条既有断言
> 在 T2 之后变红，都不是 bug：`engine_without_abbrev_index_degrades_gracefully`
> 断言「无副索引 ⇒ 零简拼层」（半音节读法走主索引，不再成立）、
> `abbrev_quota_is_floor_not_cap` 断言「`zhongguo` 不应有简拼层」（整串全拼
> 也会有末尾补全）。按项目规矩**逐条说明原断言/新断言/为什么新行为对**之后
> 改掉：前者改断**纯首字母串**（副索引真正的职责），后者改断
> **前 10 名仍是精确层**（配额不挤占精确层）。```
>
> 已知代价（未做）：半音节补全的名次偏后（#26~#49）。句首空上下文只有词频，
> 而这些词还有**整个音节没打**（`zho` 只覆盖「中」的一半，中国还有一个 `guo`）
> ——要提前就得给「未输入的音节」加罚分（A3 补全罚分的同构做法）。

### ⑱ 开发/验证环境：三件踩过的事（2026-10-02）

> **一、`just dev` 的顺序不能反：先确保 daemon 在跑，再让出引擎位。**
> 一个总线名只能一个 owner。daemon 不存在时，调试引擎会**自己拉起 daemon**，
> 而那个 daemon 一启动就按 component XML 激活 release 引擎抢走
> `org.freedesktop.IBus.Engine.xwx` —— recipe 里那 0.5 秒「让位窗口」因此完全
> 失效，**第一次 dev 必报 NameTaken**。daemon 已存在时它不会立刻回拉（实测 5 轮
> 窗口安全），所以正确顺序是：`if ! pgrep -x ibus-daemon; then ibus-daemon -rdx;
> sleep 2; fi` → 杀掉引擎 → sleep 0.5 → exec。两个场景都实测过。
>
> **二、开发期用户模型要隔离。** `just dev` 起的调试引擎原先读写真实
> `user_bigram.txt`（计数 / 造词 / Ctrl+Delete 屏蔽表三段同文件，污染后很难清）。
> 现在 debug 构建默认走 `user_bigram.dev.txt`（`user_lm_file_name()`），
> 优先级 `XWX_USER_LM_PATH` > debug 默认 > release 默认；`just install` 装的是
> release，实机不受影响。
>
> **三、别用「真实二进制 + 改过的 `XDG_DATA_HOME`」做验证。** 我这么干过一次：
> 它找不到 IBus 总线地址 → **自己拉起 daemon** → 那个 daemon 带着被删掉的临时
> 数据目录，按 XML 拉起的引擎**找不到词库**，把当时正在用的输入法弄坏了几秒。
> 要验证就走集成测试那套**私有总线**，或者干脆别跑真实二进制。
>
> 附带一条探针陷阱：`ProcessKeyEvent` 的签名是 `(keyval, keycode, state)`，
> 参数错位（keyval 传 0）会得到 `(false,)` 的假象，看着像「英文模式」。

### ⑲ ü 的匹配口径必须全层共享；简拼要「一字一字母」（2026-10-02）

> **一、一个词的名次取决于「哪个层看见它」。** 词库把 ü 写成 `v`（`lve`/`nve`），
> 用户按 `lue`/`nue` 打——`hulue` 打不出「忽略」、`lue` 打不出「略」、
> `nuedai` 打不出「虐待」。规则只有一条（`lue`→`lve`、`nue`→`nve`），但**落在
> 三处**，漏一处就残：
> 1. `segmenter::canonical_syllable` —— 唯一口径，`Segmenter::is_syllable`/`segment`
>    都走它，且**切分结果里放规范写法**；
> 2. `dict.rs::syllable_matches` —— `is_full_pinyin`/`partial_tail_readings`/
>    `segment_prefix`/`segment_input`/`MixedDfs::dfs` **五处共用**，别各写一份；
> 3. `lib.rs::build_lattice` —— **推进链里必须放规范写法**，因为 `chain.join(" ")`
>    就是查词库的 key。
>
> 第 3 处漏掉的代价最直观：候选构造完全正确，但格子拼出的 key 是 `hu lue`（查不到），
> 于是只能从简拼层兜底进来 —— 层序从 `Exact` 变 `Abbrev`，同一个词、同一个分数，
> 名次 **#1 → #59**。**「候选对了」不等于「排序也认」：要看 `spelling` 层序。**
>
> **口径（用户拍板）**：只认 üe 这一组；`lu`/`nu` 是「路/努」的合法全拼，
> **不**当 `lv`/`nv`（否则打 `nu` 会混进「女」，打 `lu` 混进「绿」）。
>
> **二、一字一字母：简拼候选的字数不得超过输入字母数。** 用户报「`wsm` 出现四个字」。
> 三个来源都要堵，少一个都漏：
> - 副索引 `lookup_abbrev`：按 key 前缀匹配，`wsm` 命中 `wsmy`（为什么要）；
> - `MixedDfs::collect` 的末位声母分支：`wei shen m` 是**字节前缀**，
>   `wei shen me yao` 也满足「以它开头」；
> - `fallback_candidates` 的前缀联想：`zho` 捞出 `zhong a guan xi`（中阿关系）。
>
> 判据用**候选全拼的音节数**，不用 key 长度（key 里 `zh`/`ch`/`sh` 可能两字母一个
> 音节）。实测 `wsm` 100 条里 78 条超长、`zgr` 83 条、副索引 `wsm` 356 条里 276 条
> 超长；修完全部归零。**只在这三层过滤**：用户 LM 里学过的词不在此列——那是用户
> 自己显式教的，不该被规则抹掉。
>
> 代价（用户已确认接受）：短输入的候选变少（打 `w` 只剩单字，不再有 我们/为什么），
> 全拼与 `nhao`/`meiy`/`women`/`diannao` 这类既有简拼输入的前 10 一条没动。

## 2. 已知的「刻意代价」（不是 bug，别去"修"）

### A3 后向 DP 的 LM 近似
候选打分用后向 DP 算「从 edge.end 到串尾的最优补全分」，
但 **LM 是左到右的**，后向拿不到精确 LM 状态，每条边只能从「无上文」起评
（bigram 下等价于只拿 unigram 分）。

**已知后果**：`xian` 的「西安」排第 18 名——双音节词拿不到 bigram 增益，
竞争不过高频单字。测试 `whole_path_beam_beats_greedy` 的断言
（`nimen` 首选从「泥」变「你」）也是这个近似的直接体现。

**为什么接受**：它只影响候选**之间**的相对排序，不影响 beam 选出的整句首选
（后者走前向精确 LM）。消除它只能回到「从 beam 幸存路径反查」
（=回到被 `BEAM_WIDTH` 钳死的老路）或引入双向 LM，都不值得。

代码注释在 `lib.rs` 的 `backward_completion` 函数级文档里，写得比这里详细。

### 回声候选的语义
照搬 librime `echo_translator`：**仅当全场一个候选都没有时才冒头**，
不是「总在末尾追加兜底项」。上屏时**不学习**（`c.echo` 时给
`learn_committed` 传 `None`），否则用户每打一次打不出字的乱码串，
引擎就学一个垃圾"词"。

### `fiao`/`tei` 不支持混合简拼切分
刻意不加进 `segmenter::SYLLABLES`——那是主切分路径，动它影响全拼行为。

## 3. 验收指标的坑

### `TOP1_AGREE` **不能**当验收门槛
两边词库/LM 不同（我们 rime-ice，librime 用 luna + 八股文 essay.txt），
对齐它等于让实现去迎合对照方的词库。只作参考。

### `NCAND_RATIO` **不能**当门槛
`MAX_CANDIDATES = 100` 截断我方候选，而 librime 的 `guo` 有 336、`shi` 有 351，
比例天花板只有 ~0.3，追它是徒劳。只用于观察趋势。

### `ZERO_ONLY_XWX` 12 → 0 是**症状**修好，不是**能力**
回声候选只让用户看见自己敲了什么、知道按空格能上屏。
简拼真正打出字要等 B3 集成完。别看着这个 0 以为简拼好了。

### `TOP1_AGREE` 只看第 1 名，**盖不住第 2~10 名整体换血**
我拿「全拼四组 `TOP1_AGREE` 不许退化」当过硬门槛，结果裸覆盖度那轮
`beijing` 的前 10 从「被 备 北 背 呗 杯」变成「被禁锢 被禁 北进 北极
悲寂 背脊」，而 `TOP1_AGREE` **一点都没动**——第 1 名一直是「北京」。

**教训**：聚合指标选错了观测点，比没有指标更危险（它会给你虚假的安全感）。
后来的判据直接点名「哪些高频单字必须在前 10、哪些生僻词不得在前 10」，
不再依赖聚合数。**能点名就点名，别让聚合指标替你判断。**

### 断言要钉「该消失的消失了」，不是「想要的存在」
`'` 分隔符出过一个**测试全绿但功能完全没生效**的 bug。
实现是 `pinyin.replace('\'', "")` 把 `'` 删掉再建格——删完就是 `xian`，
而 `xian` 本身是合法音节，`[xian]` 那条切法原样复活，
`xi'an` 与 `xian` 的候选列表**逐字节一样**。

测试没挡住，是因为它断言的是「西安**出现在**候选里」——
可西安在 `xian` 下本来就出现（第 18 名），**bug 存在时这条也是绿的**。

**消歧的定义是「另一种切法的候选消失」**（「先/现/显/线」不该在），
不是「想要的候选存在」。改成钉这个之后，把实现临时改回旧写法，
测试立刻变红。

> 这和「`TOP1_AGREE` 盖不住第 2~10 名换血」是同一类病：
> **观测点选在了不会因 bug 而变化的位置上**。
> 写断言前先问一句：这条断言在功能坏掉时会红吗？

### 交互功能要有「逐字符敲一遍」的端到端测试
recognizer 初版交付时单键断言全绿（覆盖了 `www.` 和邮箱），但真实序列是坏的：

```
❌ http://x.com  → "http:、、xcom"   ← / 被映射成顿号
❌ mailto:a@b.c  → "买:a@b.c"       ← mailto 被当拼音上屏
```

**比不做 recognizer 还糟。** 单键测试测不出来，因为没有一条跑完整个序列。

形状是这样（表驱动，`session.rs` 的
`recognized_samples_end_to_end_commit_identity`）：
**对每个字符调 `handle`，末尾 Enter，把所有 `Commit` 输出拼起来，断言等于原串。**
它在初版实现下当场复现了上面的坏结果。

> 凡是「按键序列 → 上屏文本」的功能（标点、大写、翻页、分隔符、识别）
> 都该有这么一条。单键断言只能证明每一步的局部行为，
> 证不了**整条路径**走下来是对的。

### 玩具词库测不出 mmap 的顺序问题（同一 trait，两个实现顺序语义不同）
- `SqliteDict::lookup_prefix` 按 **freq 降序**返回
- `MmapDict::lookup_prefix` 按 **字节序**返回

「声母前缀被字典序锁死」那个 bug 只在 mmap 上存在。执行者第一次做负向控制
（关掉修复看测试是否变红）时，玩具词库照样绿——因为 `SqliteDict` 本来就按
词频排，复现不了字节序偏置。

**教训**：涉及「返回顺序」的问题，玩具词库无效，必须用 `data/dict.bin`
写 `real_*` 测试。或者把断言换成只有修复路径才产生的观测量
（那轮最后断的是「逐音节配额限流」）。

> 这个顺序语义差异本身也是个坑，本轮没动它（改它超出范围），但记在这里。

### 新写的测试，要先证明它能失败
承上：怀疑一条测试是否有效时，**把实现临时改回坏的写法，确认它变红，再改回来**。
这轮就是这么验的（两条消歧测试变红、其余 apostrophe 测试保持绿，
说明观测点选对了且没有误伤）。成本几分钟，换的是「这条测试值不值得信」。

### 判据本身会腐烂，要定期重验
两次教训同构：
- `TOP10_OVERLAP` 的标签在深度 10→100 后失效，门槛「≥6.83」写的是
  一个已经不存在的单位；
- clippy「基线 6 处」清单随版本失效（`dict.rs` 三处在新版本下不再报），
  执行者无法判断自己有没有新增。

**解药**：判据要么写成不会过期的形式（clippy 已清零 → 门槛变成
「必须全绿」一句话），要么在文档里显式标注口径和测量日期。

### 延迟必须用 `--release` 测
debug 构建下同一份代码是 9.6ms 量级，release 是 1.5ms。
曾有执行者用 debug 测出「退化 7 倍」，换 release 后对上基线。
`lookup_bench` / `abbrev_bench` 一律加 `--release`。

### 验收线要按**职责范围**画，不能按 overall
我犯过：给 Block A 画了「overall `TOP10_OVERLAP` ≥ 6.0」，
但 Block A 只管 9 组里的 4 组，另外那些零分组（简拼/混合简拼/纯字母）
结构上就不可能靠 Block A 改善。**Block A 按其真实职责是达标的**
（四组均值 4.95 → 6.83），是我的门槛画错了。

### `TOP10_OVERLAP` 算的**不是** top-10 交集
`compare.py:169` 是 `len(set(rime_cands) & set(xwx_cands))`——两边**完整列表**
（各上限 100）的交集。打印的标签 `mean |rime_top10 ∩ xwx_top10|` 是陈旧的：
当初把双侧深度 10→100 时改了深度，没改指标名和标签。

**踩过的坑**：`PLAN.md` 里「全拼四组 ≥6.83 不许退化」这条硬门槛是深度 10
时代的数，我照抄进任务书，而执行者量出来是 22.90——同名不同单位，
门槛根本判不了真伪。**判退化不要比绝对值**，要拿改动前后的 probe 输出
跑同一个 oracle 做逐位对比。

### 解读 `RECALL_MISS` 要记得两个截断
`MAX_CANDIDATES = 100`（`lib.rs:61`）、`MAX_LOOKUP_RESULTS = 500`（`dict.rs:27`）。
本轮有 14 个输入的 NCAND 恰好 =100，即被截断。

### 判断「词库真没这个词」的方法与其局限
```bash
# 在 dict.bin 里搜 长度前缀 + UTF-8 词
grep -a -c -P '\x06西安' data/dict.bin
```
**局限**：这只证明词存在，**不证明它挂在匹配的拼音键上**。
我用它算过一个「上界 8.56」去反驳子 agent 的结论，后来发现界太松——
那 11 个「词库有却没召回」的词（蜗/肋/垃/偿/榜）读音根本不是那个输入。
更严谨的做法是解析 `dict.bin` 的 key→词条结构再判断。

## 5. 协作方式：什么有效

### 有效的做法
- **判据写进任务书再派活**，包括「X < 5ms 要有实测数字，不接受『应该更快』这类论证」
- **明确写「达不到就如实报，但调整标准是我的事、不是你的事」**——
  防止执行者为了凑指标去改设计或动常量
- **允许改测试断言，但必须逐条说明「原来断言什么/改成什么/为什么新行为对」**，
  不许删除或改名。Block A 那三处改动因此可复核，且断言是**加强**不是放宽
- **禁止越界**：「本任务只做存储层，不要接进 lib.rs」——出问题时定位范围小一半
- **子 agent 的报告必须自己复核**：本轮实际抓到过「把推测写成事实」
  （根目录 installation.yaml 的时间归因）和「结论对但举例错」
  （说中古/钟鼓不在词库里，实际在）

### 并行派活：文件所有权要写死
标点与排序两轮是并行跑的，任务书里各自列明「你独占哪些文件、
绝对不要碰哪些」。踩到并避开的两个坑：

- **测试总数会互相干扰**。两边都新增测试，谁看总数都对不上基线。
  判据要写成「**0 failed + 既有测试一个不许少**」，并明说
  「总数对不上不要惊慌，不要去改别人的测试」——否则很可能有一方
  看到数字不对就去动对方的断言。
- **probe 输出会被对方污染**。标点那轮如果跑对拍自证，会看到候选列表变了，
  那是排序 agent 干的。任务书要写「先判断是不是对方造成的，
  别把对方的改动记到自己账上」。

标点那轮的执行者做得很对：工作区当时有 8 个红（对方的中间态），
它**把对方的文件回滚到 HEAD 做了一份隔离副本**，证明
「HEAD + 只有我的改动 = 0 failed」，再逐个 grep 确认那 8 个失败
没有一个引用它的代码。**这是并行作业里最该有的自证方式。**

### 一个意外收获
两次 503 中断反而帮了忙。如果那个 agent 一路跑完，它会交付一个
**看起来完全达标**的 ①（预热 840ms → 0.9ms、测试全绿——因为它正打算去改
那两个失败的测试）。而里面藏着一个我任务书没覆盖的耦合：
**混合简拼从此依赖 `abbrev.bin` 存在**，而 `lookup_mixed` 的文档注释还写着
「副索引缺失不影响本查询」——注释和行为已经不一致。

是那个失败的测试（`real_abbrev_mixed_lookup` 用 `MmapDict::open()` 不挂副索引）
把耦合顶出来的。**这就是为什么不许改测试凑绿。**

## ⑲ 长串打错也能用:分段上屏 + 容错解码 + 剩余串出路(2026-10-02/03)

三期一起交付(`e43093c` 分段上屏、`40e1297` 容错解码,以及同一轮的收尾)。
验收口径与数据都留在 `examples/regression_probe.rs` 的两次输出里:基线
`/tmp/xwx_phase0_baseline.txt` 对拍 `/tmp/` 下的各期结果。

### ① 分段上屏(`e43093c`)

候选带 `Candidate.covered`(覆盖输入串开头的字节数;`0` = 未知/整串,是
字段引入前的语义,所以旧数据与未标注来源一律按整串消耗,不会退化成
「消耗 0 字节」)。会话层只消耗 `covered` 那段,剩余串留在 preedit 继续出
候选;IBus 层新增 `SessionOutput::CommitSegment`:先 `CommitText` 再刷新
预编辑区/候选窗,**不收起**。刷新失败时把前缀原样放回并返回 Err——

> **不变量:已上屏文本 + 剩余输入串 ≡ 用户敲过的全部字母。**

这是「永不静默丢字母」的可执行形式(`segmented_commits_never_drop_typed_letters`),
也修掉了改动前「选一段、后面全丢」的老行为(基线里 `beijin` 选「被禁」后
`preedit_after=""`,连 `jintian` 都丢)。

### ② 容错解码(`40e1297`)

- `segmenter::TypoSyllables`:懒构建「窗口 → ≤1 次编辑可达的规范音节 + 代价」
  索引(四类错误:插入/删除/替换/调换,Cooper 1983;代价 `-log10 P(操作)`,
  混淆概率复用 `corrector.rs` 那张表)。窗口限 2~4 字母、必须含元音、每窗口
  只留最便宜的一条读法。
- 容错格**以精确格为底**:克隆精确格,只在「走不动的位置」附近补弧,且只推
  「用过弧」的新边。
- 门槛两道:整串可精确切且有完整路径 ⇒ 不进容错;已有覆盖整串的读法且分数
  更高 ⇒ 不动它(`nih`/`zhongg` 的真简拼目标词不会被顶掉,`shenem` 的
  「什么」分数更高则照样顶掉「神而明之」)。容错候选进模糊层。

**判据演化(三次试错,都留在这里免得后人重走)**

| 做法 | 结果 |
|---|---|
| 容错弧对每个窗口都开 | 正确长链被垃圾分支饿死:每起点 64 步预算全花在 `wo+me` 这种岔路上,`womenjintianqugongyuann` 里「我们今天」缺席;长串单次 19.6ms |
| 按「第一个不可精确切分的位置」定位错处 | 音节内部的位置、别的切法造成的伪边界都会误判(把错处判到第 4 字节),反而更差 |
| 按**格上可达 + 没有出边**定位(现在的做法) | 与真实打字行为同构,一个输入只有一两个错处位置;质量最好且成本可控 |
| 长串把每起点预算降到 16 | 延迟只降 3~4ms,却饿掉整句读法(「我们今天 #1」→「我们 #1」),**已回退** |
| 容错格重建整张格 | 长串 15ms;改成「克隆精确格 + 补新边」 |
| 容错格上跑 beam 判「有没有走到底」 | **吃掉 10ms**(beam 是 O(位置×桶宽×桶内边数));改成后向 DP 的 `result[0].is_finite()`,语义等价、每条边只碰一次 |

### ③ 剩余串的反馈与出路

- **反馈**:剩余串一直显示在预编辑区(第 ① 期);候选由剩余串重新算出。
- **出路**:候选里没有任何条目覆盖整串时,补一条覆盖整串的**原样上屏**逃生口
  (`echo` 语义:不学词、不动上文,分数压到 `ESCAPE_HATCH_SCORE = -1000` 排在
  真实候选之后)。用户的另外两条路早就有:**Enter** = 拼音串原样上屏、
  **Esc** = 丢弃当前输入。

## ⑳ 延迟收口:混合简拼层的三处扫描 + 一处不确定性(2026-10-03)

第 ② 期验收时发现「单次 <5ms」没达标,而且**基线本来就没达标**——`jintian`
(7 个字母的普通词!)单次 6.70ms。剖析结果出乎意料:建格 0.13ms、beam 0.25ms、
候选打分 0.09ms,真正的大头是**混合简拼层** `lookup_mixed` 5.5ms。

### 三处纯性能优化(输出逐字节不变,对拍已验证)

1. **`lookup_mixed_full_pinyin` 的前缀区间扫描**(主因,`jintian` 5.01 →
   0.15ms)。原实现对每条切分都从 `lower_bound(prefix)` 起扫到前缀区域结束,
   而:
   - `tail` 为空时(整串就是这条切分),整个区间里**唯一会被收下的 key
     就是恰好等于 prefix 的那一条**,其余都被 `if tail.is_empty()
     { continue; }` 丢掉 ⇒ 改成一次二分直达;
   - `tail` 非空时,收下的 key 必须形如 `prefix + ' ' + <后续音节>` 且后续
     音节**首字节等于 tail 首字节**(第 908-913 行的判据)⇒ 扫描区间直接
     从 `prefix + ' ' + tail[0]` 起,并用它做 break 条件(原来用 `pb` 做
     break,会把「ji o*」「ji x*」整段扫完再退,每条都只会被丢掉)。
   - **踩过的坑**:第一版顺手把 `rest` 也改成从 `nb` 之后起算,结果判据
     `rest_syls[0][0] == tb[0]` 拿被吃掉首字母的音节的第二个字母去比,
     `ren` 的 `re n*` 一读少了 94 条(总量 113 → 19)。对拍 oracle 当场抓到,
     测试 `abbrev_quota_is_floor_not_cap` 变红。`nb` 只许参与区间,不许
     参与判据。
2. **`MixedDfs::dfs` 的字面音节分支按首字母分桶**(`zhongguor` 5.76 →
   1.83ms)。`syllable_matches` 要求 `rest[..syl.len()] == syl`(或 üe 归一后
   相等),**首字节不同的音节永远不可能匹配**,而原实现每个节点都要把整张
   音节表(~410 条)试一遍。分桶后每节点只试同首字母的十几条;桶内保持
   长度降序 ⇒ 匹配顺序、收集顺序、`MAX_MIXED_COLLECT` 截断点全部不变。
   非小写字母起点回落整表(行为不变)。
3. 顺带把 `dict.rs` 两处收尾排序改成**全序**:`freq 降序 → 词 → 全拼`。

### 一处**不确定性**发现(比性能更要紧)

做对拍时发现:**同一个二进制,两次运行候选顺序会不同**——`sh` 第 28 名
「谁」的拼音在 `shei`/`shui` 之间跳、`zh` 的简拼层整段尾序不一致。根因是
`lookup_mixed` / `lookup_mixed_full_pinyin` 从 `HashMap` 迭代出来直接
`sort_by_key(Reverse(freq))`,**同频词之间没有全序**,于是继承了 HashMap
的每进程随机迭代顺序。

已修:`dict.rs` 两处排序补上 `词 → 全拼` 收尾键(实测 `zh` 从随机变为确定)。
**残留**:`sh`(2 字母、打字中)仍会跳 —— 它的并列发生在 `lib.rs` 更上层
的合并路径上,尚未定位到具体那一步;影响面是「同频同分、仅拼音写法不同的
同一个字」的名次,用户可见的是 `谁` 的注音字段。**对拍工具读结论时要按
「同频并列忽略」处理**,别把这类差异当成退化。

### 结果(真实词库 release,`min_ms` = 30 次取最小)

| 输入 | 基线 | 优化前 | 优化后 |
|---|---|---|---|
| `jintian`(普通词) | 6.70 | 6.63 | **1.87** |
| `zhongguor` | 5.56 | 5.71 | **1.88** |
| `xian` | 3.52 | 3.51 | **0.94** |
| `zgr` | 1.23 | 1.24 | **0.75** |
| `zhongg` | 3.42 | 3.22 | 3.73 |
| 最大(病态长串) | 8.90 | 10.21 | **6.59** |

### ⚠ 修回两个被静默丢掉的胜例(oracle 的盲区)

第 ② 期收尾时,`shenem → 什么 #1` 和 `womenjinxtianqugongyuan → 我们今天 #1`
两个胜例**悄悄退回了基线行为**,而且躲过了当时的对拍检查——因为对拍只比
「列表有没有变化」:**退回基线 = 没有变化**,于是最坏的一种退化正好是盲区。

根因是容错格「克隆精确格 + 只补新边」时的**链起点范围**搞错了:
`shenem` 的「什么」需要 `[shen][me]` 这条**从 0 起、止于 6** 的整链边
(`em`→`me` 的调换弧覆盖错处 5)。当时把重新枚举的起点限制在
`stall − MAX_TYPO_WINDOW` 之后(想省成本),起点 0 被排除,这条边永远
生成不出来,「什么」整条消失。

- 修:**从 0 枚举到最深错处**(错处之后的部分由弧沿链走完,不需单独当起点),
  并且**每个起点只枚举一次**(不再对每个错处各来一遍,长串开销从 5 份降到 1 份)。
- 教训:对拍判据必须**点名目标词**(「`shenem` 第 1 名必须是『什么』」),
  不能只看 diff——退回基线在 diff 上是隐形的。
- 教训二:我一度按「最深错处才是真错处」把所有错处压成一个来提速,
  结果 `womenjinxtianqugongyuan` 的「我们今天」又丢了(它靠的是覆盖
  位置 4/7 的弧,不是最深的 8)。**已回退**,`first_stalls` 的全部位置都保留。

### 确定性补完 + 一处重复计算(2026-10-03)

## ㉑ 分段上屏改成「确认段留在组合里」(方案 b,2026-10-03)

**起因(用户报的交互问题)**:一长串拼音里选了一段之后,按退格键删的是**剩余串
的末位字母**,而用户的心智模型是「回退到上一步重新选」。根因是第 ① 期把选中的
段立刻 `CommitText` 交给应用了——交出去就收不回来,退格除了删字符没别的可做。

**改法**:选中的段不再立刻交给应用,而是进 `InputSession.confirmed`(确认段栈),
预编辑区显示 = **确认段文本 + 剩余拼音串**;整个组合结束时才**一次** `CommitText`。

- `SessionOutput::CommitSegment` 变体**删除**——不再需要「上屏一段还留着组合」
  这种语义;确认段走 `Updated`(只刷新界面),`xwx_ibus` 侧的对应分支一并删掉。
- 触发撤回不了的问题自然消失;`append_to_commit` 只剩 `Commit` 一条分支。
- **退格规则**(按用户口径):只要还有已确认段,退格就**回退上一次确认**——把那段
  消耗掉的字母原样还回输入串、重新出候选,**不看光标位置**。选完一段后光标落在
  剩余串末尾(用户还在继续打字),若要求「光标在分界处才回退」,用户就得先把剩余
  串一个字一个字删光——那正是要修掉的手感。全部退回之后才回到文本编辑惯例。
- **记账(造词缓冲 / 上屏尾部 / UserLM)推迟到组合结束**(`replay_confirmed`):
  中途确认的段还没交给应用,用户随时能退回来——若在确认当时就写 UserLM,回退
  就得做「反学习」。
- 结束路径统一:整串候选被选中 / 回车 / 标点 / Verbatim 字符 / 切英文 / 只剩确认
  段时空格 —— 都走 `commit_selection`(确认段 + 这一条)或 `finish_with_raw`
  (确认段 + 原样字母),**一次**交给应用。
- **边界状态**:剩余串可能被退格删空而确认段还在(`composing()` = 两者任一非空)。
  这个状态下回车/空格/Esc/退格都必须按「组合仍在」处理,否则用户选过的段既上不了
  屏、也退不回来——四个分支的守卫都从 `!pinyin.is_empty()` 改成 `self.composing()`。
- **焦点切换**:`reset_for_focus_change()` 现在返回「已确认但还没交给应用」的文本,
  `xwx_ibus` 的 `reset_state` 补一次 `CommitText`——用户明确选过的内容不能因为切
  窗口就丢。未确认的剩余字母仍按原有语义丢弃(那是「还没选」的内容)。

**行为变化清单(换会话接手时需要知道)**
1. 选中的段不再立刻落进应用,整串结束时才落(一次 `CommitText`,不是多次)。
2. 退格:有确认段 → 先回退选择;没有确认段 → 照旧删光标前一个字符。
3. Esc 丢弃**整个**组合(含已确认段)——它是「取消这次输入」,与主流输入法一致。
4. 标点/回车/切英文会把整个组合一次上屏,且标点拼在末尾。

**验收**:`just verify` 全绿(247 单元 + 49 集成等,clippy `-D warnings`);
A 段(候选列表)与改动前**逐字节相同**——这次只改会话/IBus 的交接时机,没碰解码与排序;
新增单测 3 条(确认段留组合 + 退格回退 + 结束时一次上屏),D-Bus 集成测试
`selecting_a_prefix_candidate_keeps_the_remaining_pinyin_composing` 按新语义重写
(确认时零 `CommitText`、退格还回字母、结束时一次提交 `你好北京`)。

## ㉒ 「一字一字母」收严:`yij` 不再出「已经是」+ 补全读法回到精确层(2026-10-02)

用户报的两条(「`yij` 会出现『已经是』」「简拼排序像没排序,全拼很好」)查下来是
**同一条规则的两个面**:判据只看字数,层序把补全读法当成了缩写。

### 一、`yij` → 已经是:只挡了「字数 > 字母数」

`MixedDfs::collect` 的「一字一字母」原先比的是「候选字数 ≤ 输入字母数」,
于是 `yij`(3 字母)配 key `yi jing shi`(3 字)刚好放行——而这个 key 里「是」
那个音节**一个字母都没打**(`yij` = `yi` + `j(ing)`,`shi` 是字节前缀扫进来的)。
实测它在简拼池里按词频排第 12/500,平时被 `ABBREV_QUOTA=5` 截住;换
`yijs`/`yijshi`/`yjshi`/`yijingshi` 它就是第 1~2 名——症状随时会冒出来。

> **判据改成**:`mid_syllable` 时,key 在前缀之后**不许再有空格**(= 不许再起音节)。
> 等价口径:**每个字至少对应一个打字字母**。

## ㉖ D5:翻页/数字/空格/点击统一到「一个权威下标」(2026-10-03)

### 问题形状

四个出口各用各的坐标,任一处改动都会让「面板显示的那条」与「上屏的那条」分叉:

| 出口 | 旧实现取的是 |
|---|---|
| 面板渲染 | `page` 字段切出的**当前页切片** + 页内下标 |
| 数字选词 | `self.candidates[n-1]`——**全局**下标,与页码无关 |
| 空格上屏 | `self.candidates[self.cursor]`——全局下标 |
| 点击选词 | `InputEvent::CandidateClicked(index)` 当**全局**下标用,而面板回传的是页内序号 |

翻页只动 `page`、不动 `cursor`,于是「第 2 页首项显示、第 1 页首项上屏」;
`CursorDown` 越过第一页后线上表仍是第 1 页(页内下标被钳在 8),而会话高亮
已经走到第 10 条。

### 修法(单点权威 + 一条映射)

- `InputSession` 删掉 `page` 字段:**唯一权威坐标是全局 `cursor`**,
  `page()` = `cursor / page_size`(只读推导,见 `session/view.rs`)。
- 翻页 = 把 `cursor` 移到目标页首项(`goto_next_page`/`goto_prev_page`,
  末页/首页钳位、不 wrap,与既有按键行为一致)。
- 数字与点击**共用同一条映射**:全局 = `page_start + 页内偏移`;
  `InputEvent::CandidateClicked(index)` 的契约明确写成**页内下标**
  (面板只看得见当前页,它也只能回传页内序号)。
- 线上坐标系保持「当前页切片 + 页内 cursor」。

### 为什么**不**按审查推荐发整表 + 绝对 cursor

实测(`ibus_lookup_table` 构造 + 转 `OwnedValue`,每键一次):

| 候选数 | 构造+序列化 |
|---|---|
| 9 条(一页) | 146 µs |
| 500 条(`MAX_LOOKUP_RESULTS` 上限) | **7.5 ms** |

500 条那一档单这一项就吃掉 12ms 热路径预算的一半以上,所以走页内方案:
页内 cursor 恒 < `page_size` ⇒ 面板无论按「绝对下标」还是「页内下标」理解
`cursor`,算出的页码都是 0,点击回传的都是页内序号——两种面板口径在本方案下
**得到同一个下标**。旧实现的缺口不是坐标系,而是**会话少做了那条映射**。

### 证据(旧实现必红)

- 单测(`session/tests/paging_delete.rs`,5 条):`digit_selects_within_the_current_page`、
  `digit_without_a_candidate_on_this_page_is_a_noop`、

### 有意变更(旧 golden 作废,原文保留在此)

## ㉗ D9:分隔符(`'`)约束兜底,回声回原文(2026-10-03)

### 两个缺陷(都已复现)

`'` 原本只在**格构建**里当强制切分点(`collect_chain_edges` 拒绝穿过它的音节),
两条路绕开了它:

1. **兜底路径**把清洗串当普通串重新切分。「最长可切分前缀」在 `xianq` 上切出
   `xian`——穿过位置 2 的分隔符——于是 `xi'anq` 的前 12 条候选全是
   `pinyin=xian` 的「先/现/显/线…」。实测(真实词库):
   `xi'anq` → 0|先 1|现 2|显 3|线 …(全部 key `xian`);
   `'` 在整串解不出时**形同不存在**。
2. **回声候选的文本来自清洗串**:`zz'zz` 的回声 `word` 是 `zzzz`,空格/点选
   上屏成 `zzzz`——用户敲的分隔符被静默吞掉。

### 修法(一条判据两处复用 + 文本只认原文)

- 判据抽成 `ImeEngine::syllable_crosses_boundary(pos, len, bounds)`
  (**与格构建逐字相同**:分隔符落在音节内部才非法,落在音节边界上合法),
  格构建改为调用它;新增 `key_respects_boundaries(key, bounds)` 用于
  「音节怎么切由词库决定」的候选(key 是空格分隔的音节串)。
- `fallback_candidates(pinyin, ctx, bounds)` 现在收边界:
  ① 选「最长可切分前缀」时要求**存在一条不穿界的切法**;
  ② 逐条切法再筛一遍(穿界整条丢);
  ③ 末尾统一的 retain 加判据 —— 前缀联想分支的 key(`zh'on` 的 `zhong`)
  也是这么被挡住的。`bounds` 为 None 时三个判断恒真、不扫 key,无 `'` 输入
  **逐字节不变**。
- 回声与逃生口的文本改为取自 `raw`(归一化前的原文),覆盖范围仍按干净串算、
  再经 `fill_covered` 映射回原文——`xi'anq` 的「西安」因此 `covered = 5`
  (`xi'an` 的原文字节数),分段上屏吃掉它之后 `q` 仍留在组合里。
- 顺带核实:简拼/混拼层**本来就**在含 `'` 时整层跳过(见 `lookup.rs` 的
  `if bounds.is_none()`),所以不存在「兜底堵住了、简拼层又漏回来」的缺口。

## ㉞ 容错解码的编辑预算真正落到「整条路径」(codex 审查 D13)(2026-10-03)

审查第一批 D13(P2)。

- **问题**:`MAX_TYPO_EDITS` 只卡**单次链枚举**(`engine/lattice.rs:506,592` 的
  `typo_edits < MAX_TYPO_EDITS`)——一条「音节级 ≤1 编辑」弧落成 `LatticeEdge`
  之后只剩 `typo_penalty` 罚分,后向 DP 与 beam 都拿不到「这条边用了几次编辑」,
  于是**两个各错一处的词**能拼出一条两次编辑的读法,与常量文档里「整条路径
  最多允许的编辑次数」的口径自相矛盾。触发面窄(要有两个 stall 各配一次编辑),
  但属于「口径说不清就不算数」的漏洞。
- **改法**:
  - `engine/mod.rs` 的 `LatticeEdge` 新增 `edit_count: u8`;`collect_chain_edges`
    的 3 处构造点带上它(音节级编辑弧 = 1、空词弧 = 1、精确/模糊边 = 0)。

    字母判成两次编辑,与 `MAX_TYPO_EDITS` 的语义不符。
  - `backward_completion` 改成 `result[剩余预算][pos]` 两维递推
    (`engine/lattice.rs`):边自身的分数(词频项 / LM 近似分 / 两种惩罚)先算
    一遍再按预算合并,LM 调用次数不随预算翻倍;`result[r][pos]` 单调不减
    (用不完的预算不强制花掉)。
  - 候选补全扣掉首边已用预算(`engine/lookup.rs::lattice_candidates_scored`):
    `remaining = (预算上界 - edge.edit_count)`。
  - 前向 beam 的状态带 `used_edits`(`engine/mod.rs::BeamNode` + `engine/decode.rs`),
    超预算的分支不再扩展。
- **验证**(旧实现必红,已实测):

    DP 单维)⇒ 前 3 条用例**红**;还原后全绿。
  - `just verify` **357 用例全绿**(287 engine + 6 ibus + 9 bin + 55 集成),
    clippy `-D warnings` 无输出。
  - 真实语料对拍:`regression_probe --format v1` 2322 行与

  - 延迟:`perf_probe --repeat 3 --prewarm` 稳态 p50 0.271ms / p95 1.508ms /

## ㊳ Q4 第四步：读取端的区段校验

- **问题**（Q4）：`dict/mmap.rs::from_bytes` 只校验长度/魔数/版本，**三个区段起点直接
  采信**；每次 `record()`/`slice()` 都拿它们做加法，越界只能靠 `get` 兜底——报错离谱
  （「偏移 2^60 越界」而不是「头部损坏」），某些布局还能悄悄读到别的区段（静默错数据）。
- **做法**：读完头部后立刻校验「header ≤ records ≤ strings ≤ entries ≤ 文件长」，
  并对 `pinyin_count × RECORD_LEN` 做 **checked 乘法**、证明记录数组落在 strings 区
  之前；不合法返回 `DictError::Corrupt("区段顺序/范围不合法…")`。
- **用例**：`dict/tests.rs::corrupt_section_offsets_are_rejected_at_open` 构造
  「records 起点跑到 strings 之后」的头（临时文件 + `MmapDict::open`），断言必须报错
  且信息点名区段问题——旧实现会**照常返回 Ok**，所以这条在旧实现上是红的。
- **待做**：`dict/abbrev.rs` 套用同一套；主副索引同源标识/哈希（发布契约）。

## ⑤⑥ 第三批第 5 项：受控中英混输——大写字母起头的英文单词

- **用户症状**：中文模式下敲 `Shift+H` 只上屏一个 `H`，后面的 `ello` **回到拼音**
  （候选列表给出「额/饿/恶…」）⇒ 英文单词没法自然打出来，只能先按 Ctrl+空格
  切模式、打完再切回来。
- **做法（显式控制，不是猜）**：会话新增 `english_run` 状态——
  - **进入**：`Verbatim(大写字母)` 且身上没有未上屏的组合（即 Shift+大写字母**起头**）；
  - **持续**：跟随态里的字母逐字上屏（走 `commit_raw`：不进候选、不学习、不进
    造词缓冲，与单字母 Verbatim 同一条路）；大写字母也照走（`Abc` 这种词能打）；
  - **结束**：任何**非字母**事件（空格/标点/回车/退格/Esc/翻页/模式切换）——
    落在 `handle` 开头的一行 `matches!` 里，不散落在各分支；焦点切换
    （`reset_for_focus_change`）另加一条显式清除。
- **为什么是「大写起头」而不是「判断这串像不像英文」**：后者已被实测证伪三次
  （见看板卡 `t-mur20d0m-kvtj99` 的评论 `c-murwgd04-px27ev`）：简拼层对**任何**
  字母串都能造出覆盖整串的读法（`hello` → 赫拉利），所以「像不像拼音」不是结构
  问题而是词频问题；而「原样上屏」这条候选目前还没有自己的层与桶（借用 `Exact`
  + `ESCAPE_HATCH_SCORE`），一推到列表里就会插到简拼层前面，破坏两个排序不变量
  用例。因此先做**不需要新层、不需要数据**的那一半。
- 定向用例：`session/tests/punct_verbatim.rs::uppercase_start_keeps_the_rest_of_the_word_in_english`；
  **旧实现实测红**：`e 应逐字上屏而不是进拼音: Updated(SessionUpdate { preedit: "e", … })`。
- 验收：`cargo test -p xwx_engine --lib` **312 passed**、clippy 0。
- **仍未做的**：(a) 给「原样上屏」单独定层（用户在小写状态下打英文单词仍未解决，
  需要动排序键）；(c) 英文词表数据。

## ⑤⑦ 中英切换的两处修正（用户实测反馈）

- **症状 1：鼠标在输入框里点一下就被切回中文。** 根因是 ⑤④ 加的那条
  「焦点切换把模式收回中文」——鼠标点输入框会触发 IBus 的 `FocusOut`/`Reset`，
  于是「英文打一半点一下输入框」直接变中文，等于没法连续打英文。
  **修法：回退 ⑤④ 的模式复位**（`reset_for_focus_change` 只结束「英文跟随」，
  不动 `english_mode`），`toggle_ascii` 的文档一并改回「模式跨焦点保持」。
  ⑤④ 当初的理由是「顶栏没有任何中/英指示」——⑤⑤ 的 IBus Property 做出来之后
  这条兜底就没有必要了，而且它的代价（点一下就复位）比收益大。
- **症状 2：状态栏属性显示成开关控件。** 根因是属性类型用了
  `IBUS_PROP_TYPE_TOGGLE`（面板渲染成开关）。**修法：改成
  `IBUS_PROP_TYPE_NORMAL`**（普通菜单项，点击即触发 `PropertyActivate`）；
  因为 NORMAL 属性能拿到的 `state` 恒为 0，`PropertyActivate` 相应改成
  「按当前模式取反」而不是读 `state`（否则点一下只能切到英文关）。
- 定向用例：`session/tests/basic.rs::focus_change_keeps_the_mode`——
  **旧实现实测红**（`焦点切换不应改变中/英模式`，即用户报的现象）。

## ⑤⑧ `just dev` 为什么可能跑的不是新二进制（已修）

- **真相**：`just dev` 的 recipe 里第一步就是 `cargo build -p xwx_ime`，跑的也是
  `{{target_dir}}/debug/xwx_ime`——**不存在「没重编译」的问题**（实测：调试二进制
  时间戳比提交还新）。坑在**名字之争**：会话里的 ibus-daemon 是按 component XML
  拉起引擎的，而 XML 指向的是 `~/.local/bin/xwx_ime`（安装版）。于是 `just dev`
  把调试引擎拉起来时，谁先拿到 `org.freedesktop.IBus.Engine.xwx` 就看时序：
  daemon 抢先拉起 release 引擎时，调试引擎 `request_name` 失败、**直接以
  `NameTaken` 退出**，打字仍然落到旧二进制上——现象就是「`just dev` 不是新二进制」。
  （我在自己的私有总线 e2e 里踩过同一条：`Error: NameTaken`。）
- **修法**：`src/main.rs` 占名改成
  `request_name_with_flags(ENGINE_SERVICE, ReplaceExisting | AllowReplacement)`
  ⇒ 后来者接管名字，旧持有者收到 `NameLost` 后不再被 daemon 使用。
  这样 `just dev` 一定服务新构建，不必先 `just install`。
- **验证**（私有总线，同一条总线上起两个实例）：第二个实例**活着**且日志里
  `NameTaken` 计数为 **0**（旧实现下它必然带着 `NameTaken` 退出）。
- `just dev` 另外加了一行提示，打印它要 exec 的调试二进制路径。
- 注意：`just install` 仍然是「装到系统、给 GNOME 输入源用」的那条路；
  **调试验证不需要它**。

## ⑤⑪ 阶段 2A：缩写音节 + 字面尾链的**可穷尽约束匹配**（修 `ztailan`/`ztai`）

  （另有 28 行 `-inf` 差异来自阶段 1 的 `edit_count` 修复，见 ⑤⑩。）
- **已知副作用（阶段 3B 要收拾）**：`ztailan` 现在只有 1 条候选——因为「已经有一条
  覆盖整串的读法」这条**存在性否决**会关掉容错/简拼格的后续探索（codex 说的

## ⑤⑬ 阶段 2B：音节级转移索引（缩写弧剪枝不再走 186 万条 key 的二分）

- **索引**：`scripts/build_syllable_graph.py` 把 key 空间编成音节级树（60B 头 +

  2,819,020 边 / 62.0MB / 生成 42s；产物自检（头自洽 + 抽 400 条 key 走通到底）。
- **读取器** `dict/syllable_graph.rs`：`open / child / children_starting_with / walk / node`。
  与 `abbrev.bin` 同一套约定：可选数据、损坏只报错不 panic、**同代校验用头部 n_keys
  与词库记录数比对**，不符就不装配。`Dictionary::syllable_graph()` 默认 None；
  `DictStore` 必须转发——漏转发＝静默退回二分（与 key_prefix_state 同一个坑）。

  链已不是任何词条 key 前缀时直接剪整棵子树。索引缺失/节点未知时原样退回
  key_prefix_state，回退路径仍被全部单测覆盖。装载点：`src/main.rs`

- **等价性（本次最重要的证据）**：同一个二进制，有索引 vs 无索引（把

- **未取到**：端到端 `perf_probe` 在本机负载 14.2（20 核）下 p95 15.9ms，而回退路径

## ⑤⑭ 阶段 3B：整句接管的判据（基线补偿 + 整句不再继承逐词惩罚）

- **根因**（量化，非猜测）：LM 的「无证据基线分」（万象实测 −11.605767，见
  `examples/lm_word_probe.rs`）原先**按词数复付**——多词读法每多一个词白扣一次
  基线。实测 `chuzaina`：「杵在那」−19.4889 vs 「出+在+哪」−20.0733，差 0.58 的
  表面差距底下是 12.19 的记账偏差（先验组合本来赢 5.10）。
- **修法**（两处，都不引入阈值）：
  1. `engine/decode.rs`：`lm_floor` 补偿——第 2 个词起扣掉基线，保留各词**高于
     基线的条件证据**；只在 `per_word_penalty == 0.0`（全拼整句路径）生效，简拼层
     口径不动；模型没有基线概念时 `floor_log10()` 默认 0.0 ⇒ 原式不变。
  2. `engine/lookup.rs`：整句路径传 `per_word_penalty = 0.0`（原先继承了简拼层的
     `ABBREV_PER_WORD_PENALTY = 1.2`，三词读法白扣 3.6）。
  3. 整句门槛去掉「已有覆盖整串的候选」一条（`has_reliable_phrase` 的位置由分数
     判断顶上，不加旗标）。
- **结果**：`chuzaina` → #1 出在哪(−17.6733)、#2 杵在那(−19.4889)；`nihao` →
  #1 你好(−15.9666)；`womenjintian` → #1 我们今天(−16.6848)。验收用例
  `engine/tests/sentence_gate.rs` 两条（可靠性端带/不带 LM 都绿；不可靠端需 LM，
  缺模型时明确跳过）。
- **漂移点名**（v1 对拍 734 行 → 实为 **11/44 个输入、首位变化 0 个**）：全是新增
  `freq=0` 整句读法，各输入的 #1 仍是词频 50 万级正确词。逐条清单见看板卡
  `t-murybima-lnpbsv` 评论 `c-mus08flc`。
- **门槛**：`cargo test --workspace` **393 passed / 0 failed / 1 ignored**、clippy 0；
  perf 在负载约 13 时 p95 **12.305ms**（超线 0.3ms；此前同负载下未改动的基线也在
  12.6~15.9ms，安静时历史值 11.1~11.8ms）——记为待安静环境复测。

## ⑤⑯ 阶段 4：最低档整串词条不再算「可靠覆盖」（chuzaina → 出在哪）

- **判据**：`engine/mod.rs::FILLER_FREQ_TIER = 100` —— `freq == 100` 是词库源数据的
  「未知/极低频」约定值（抽样 233,025 条里 164,371 条 ≈70% 落在这一档，其余 1/2/3/5…；
  生成器只有 `FREQ_MAX`、没有下限）。整串覆盖者**全是**这一档 ⇒ 视为没有可靠覆盖。
- **落点**：`engine/lookup.rs` 整句段的置顶判据——有可靠覆盖时仍按原规则置顶，
  没有时置顶**本段刚产出的整句候选**（`sentence_keys`）。等价于上游
  `has_reliable_phrase`，且**不动任何分数**。
- **效果**（带 LM 实测首位）：`chuzaina` → **出在哪**（原「杵在那」）；`womenjintianquxian`
  → 我们今天去西安、`womenjintianqbj` → 我们今天去北京、`wmjtqbj`/`womenjtqbj`/`zmgai`/
  `nihao`/`ztai`/`ztailan`/`zguor`/`xian`/`daishixian` 全部不变。
- **门槛**：`cargo test --workspace` 单元 **320 passed / 0 ignored**（两条验收用例都绿，
  不再有 ignored）；clippy 0；v1 对拍漂移 **400 行、首位变化 0 个**（与改前同量，本规则
  没有新增漂移）；eval daily 召回 **12/12**、mixed **13/14**（未召回 `jintqbj`，旧问题）。

## ⑤⑲ 叠字母纠错：`shanghaai` → 上海

## ⑤㉒ 两条诊断（`jintqbj` 的机制、候选池为何还不能删）

**一、`jintqbj` → 今天去北京（期望「今天请病假」）不是结构缺口，是这一层的打分口径。**

- 两种读法都是**单条词条**：`qu bei jing`→去北京、`qing bing jia`→请病假（`qbj`
  实测里「去北京」#2、「请病假」#6，同一层、同样 3 个缩写音节、弧惩罚相同）。
- 这一层（简拼/混拼池 `lookup_mixed` → `abbrev_candidates`）给候选打分时把**整个
  候选文本当成一个词**去问 LM：`P(去北京 | 上文)`、`P(请病假 | 上文)`。两个短语
  都不在万象词表里 ⇒ 都回落「非词配兜底分」⇒ **条件证据实际没参与排序**，
  排序由词库词频决定（去北京更高）。
- ⇒ 要修它就得让这一层按**词串**打分（把词条分解成词库里的词、逐词累加先验与
  条件 LM，上下文逐步推进），也就是阶段 3「统一路径搜索/打分」把这条旧通道并进来
  的那一步。语料里保留人工期望（「今天请病假」），不改语料迁就实现。

**二、候选池（`lookup_mixed` 的 `partial_tail_readings` 那条补全路）现在**不能删**。**

进格子的补全弧按设计只对「含元音」的窗口开放（`window_has_vowel`），而池子还要服务
**纯声母**窗口：`sh` → 是/时/事、`zh` → 这/中…（`engine/tests/completion.rs` 的
`initial_only_prefix_recovers_all_finals` 正是钉这条的）。两者是不同的能力：
池子 = 「整串都还没打完」的通道，格子弧 = 「前面有词、末尾少打一个字母」的通道。

## ⑤㉓ 更正 ⑤㉒ 的第一条诊断：`jintqbj` 是**模型自己的判断**，不是打分口径的锅

⑤㉒ 的推断是「简拼层把整个候选文本当一个词问 LM ⇒ 去北京/请病假都不在词表 ⇒

  条件证据排序了。`jintqbj` 给「今天去北京」是**模型自己的条件概率判断**。

## ⑤㉔ 投影层规则的**过粗**：它会挤掉「真短语但词频缺失」的正确读法（两次尝试均已回退）

**现象（日常短语 × 5，全部是「正确项被挤到 #2」）**：

| 输入 | 排序前首位（正确） | 被投影规则换上来的 | 依据 |
|---|---|---|---|
| `zaodianxiuxi` | 早点休息 `freq=100` | 早点修鞋 `freq=0` 组合 | LM：休息 -7.17 vs 修鞋 兜底 |
| `womashangdao` | 我马上到 `freq=100` | 我马上道 `freq=0` 组合 | 到 -8.02 vs 道 兜底 |
| `jintiantianqizenmeyang` | 今天天气怎么样 | 今天天气怎么养 | 怎么样 -5.38 vs 怎么养 -6.62 |
| `nizaiganshenme` | 你在干什么 | 你再干什么 | 在 -10.19 vs 再 兜底 |
| `nihaoshijie` | 你好世界 组合 | 你好时节 `freq<=100` | daily 的 MRR 就是被这条拖到 0.958 |

机制：`FILLER_FREQ_TIER` 只说明「词库里没有真实词频」，**不说明这个读法差**；
但现规则一律把组合候选提到首位。

**尝试 A（守卫：只有当挑战者 `score` 更高才换位）**：上表 5 条全部修正，
daily MRR **0.958 → 1.000**、keystrokes MRR 0.877 → **0.919**；
但把 `chuzaina` 打回「杵在那 #1」——因为组合候选「出+在+哪」的 **score 更低**：
LM 的「无证据基线分」按词复付（每个词各付一次 -11.605767），组合读法天然吃亏，
而 `floor_log10()` 自 2026-10-03 那次 3B 回退后**引擎里已经没有人在用**。
`chuzaina` 是验收形态，不能退化 ⇒ **尝试 A 回退**。

**尝试 B（两边都按词串口径比：切词串 + 逐词先验/条件 LM）**：更糟——
`shanghaai` 掉到「上」#1、edits MRR 0.728 → 0.564。投影层不该承担口径改动 ⇒ **回退**。

⇒ 结论：「填充档词条 vs 组合候选」谁该在首位，**不能靠投影层的档位规则判**，
必须先消掉打分本身的**逐词基线复付**不对称（让两条路的 score 可比），
这正是阶段 3「统一路径搜索/打分」的活，做完之后这条投影规则可以简化甚至删掉。

**工具**：`examples/lm_word_probe.rs` 现在支持传参 `lm_word_probe <上文> <词1> <词2>…`，
逐词推进打印分数与链合计（本轮就是靠它证明「万象明确偏好正确词」）。

## ⑤㉕ 尝试 C：把 LM 分数改成「相对兜底基线的证据量」——**全线下滑，已回退**

做法：在 5 个把 LM 折进候选分的地方（`decode.rs:135/354`、`lattice.rs:223/374`、
`lookup.rs:530`）统一改用 `logp - floor_log10()`（兜底 = 0，不按词复付）。

实测（同源码 A/B，44 输入对拍之外另看形态与语料）：

| 观测 | 改动前 | 改动后 |
|---|---|---|
| `wmjtqbj` | 我们今天去北京 | **我们就提前北京** ✗ |
| `womenjtqbj` | 我们今天去北京 | **我们就提前北京** ✗ |
| `chuzaina` | 出在哪 | **杵在那** ✗ |

**为什么错**：`logp - floor` 把「没有证据」变成了**逐词的奖励**——

## ⑤㉖ 投影层的填充档判断改成**按词串口径比**（每候选一次基线）——daily MRR 回到 1.000

改动只在投影规则的一支里：首位是填充档词条（`freq <= FILLER_FREQ_TIER`）时，

1. **词面必须取候选自己的汉字**：切词只回「每段几个音节 + 词频」，

## ⑤㉙ 尝试 D：简拼层「整串落底时换词串口径」——mixed MRR 退化，已回退

做法：`abbrev_candidates` 里对「整串口径落到底 + key ≥2 音节」的候选

## ⑤㉚ 阶段 3 的整层切换计划（下一步执行的施工图）

### 为什么必须是整层切换
④㉙ 及之前四次实验已经把边界探清：**只在部分候选上换打分口径**一律破坏层内可比性
（投影层守卫版丢 chuzaina、投影层词串口径版丢 shanghaai/edits、全局相对基线版全线掉、
简拼层落底换口径版 mixed MRR 0.929→0.821）。所以阶段 3 的第一步不是加规则，
而是**选一类输入，把它的候选整层切到同一口径**。

### 切换范围（第一类，选最小风险面）
只切**纯缩写输入**（key 全部由「一个字母 = 一个音节首字母」构成，如 wmjtqbj / zmgai / ztai），
它们今天走 `lookup_abbrev` + `lookup_mixed` 两个旧通道（`lattice.rs::abbrev_candidates` 里合并）；
不切混拼（`womenjtqbj` 这类含字面音节的）、不切整串精确输入。

### 施工步骤（每步一次提交，每步都过门槛）
1. **准备对拍**：把 44 输入对拍里「纯缩写类」单独切出来做一份清单（另存
   /tmp/xwx/probe_abbrev_before.txt），并记录四套语料当前指标作基线。
2. **接格子**：在 `abbrev_candidates` 里对纯缩写输入改走**格子路径**——
   `collect_chain_edges` 已有的简拼弧 + `abbrev_syllables` 就是它们的读法来源，
   格上逐条边的打分与整串/精确候选同源（`decode.rs` 的边分公式）。
   旧通道**保留但不出候选**（回退点：一个常量开关切回去）。
3. **层序与配额**：格子来的简拼候选仍标 `SpellingKind::Abbrev`，层序不变；
   `merge_with_abbrev` 的配额逻辑照旧（它按 RecallSource 分层，不关心来源实现）。
4. **验收**：纯缩写清单逐条点名差异；四套语料不得低于当前值
   （daily 12/12·MRR 1.000、mixed 13/14·0.929、keystrokes 12/12·0.877、edits 6/6·0.728）；
   ztai→状态、ztailan→状态栏、wmjtqbj/womenjtqbj/zmgai/zguor 不许退化；
   perf 同条件 A/B 不可区分；clippy 0；对拍非纯缩写部分 0 变化。
5. **收尾**：HANDOFF/PLAN-history/VERIFY 同步；看板阶段 3 卡写评论。
   这一步做完，`lookup_abbrev` 才谈得上删除（阶段 5）。

### 预判的坑（来自已有记录）
- 简拼格构建成本：2048 链/起点时实测 ≈11ms，破 12ms 门槛 ⇒ 必须带
  `MAX_TOLERANT_CHAINS_PER_START` 同级的预算，且**先量再切**；

- 纯缩写输入没有 `'` 边界，`bounds` 分支一次都不进，与旧通道一致。

## ⑤㉟ 缺口机制查清：格子**能表示**这些读法，是**打分**把它们挤出候选表

以 `ztai`→状态 为例，逐层查过：

1. **读法枚举没问题**：简拼弧（`lattice/build.rs:294-320`）的 `len == 1` 分支把 `z`
   当作 `zh` 的简写（注释写明对应 RIME 的 `derive/^([zcs])h(.*)$/$1$2/`），
   `segmenter::abbrev_syllables("z")` 里**包含 `zhuang`** ⇒ 「状」这条边有；
   `tai` 是完整音节 ⇒「态」这条边有 ⇒ **「状+态」这条路径在格子上存在**。
2. **卡在打分**：`best_chain_candidates` 只回 `ABBREV_CHAIN_NBEST` 条 n-best，
   而路径分是「**逐词**词频先验 + **每弧** `ABBREV_PENALTY`」累加——「状+态」
   两个字条都很低频、还背两次简拼惩罚，于是输给单字读法（摘/宅/寨），
   状态**掉出候选表**（前 10 都没有）。
3. 反观旧通道：它直接拿整串去查**词条**（状态本身就是词条，词频高），
   所以在这类输入上全面占优。

**下一步的修法（一句话）**：**当一条路径的整串恰好是词库条目时，按该条目打分**
（词频 + LM，套用已经落地的「每候选一次基线 + 词串口径」），而不是把逐词分数相加。
这是"统一词匹配/打分"的核心动作：读法来源统一到格子之后，**打分也统一到格子**，
旧通道的"整串查词条"优势就不再是它独有的了。

**验收指标**：20 条纯缩写清单里「正确读法出现在候选前 10」的比例——当前 **5/20**；
修完这条应当显著上升，且四套语料与 v1 对拍不许退化。

## ⑤㊱ 尝试 E：路径整串命中词条时按条目打分——**无效且 mixed 退化，已回退**

做法（按 ⑤㉟ 的修法）：在 `best_chain_candidates` 里，若某条路径的整串恰好是词库条目，
就按该条目打分（词频 + LM，`lm - floor` 一次基线），与路径分取更高者。

实测：**指标纹丝不动**（20 条纯缩写仍是 #1 正确 5/20、进前 10 5/20），
mixed 语料 MRR **0.929 → 0.893** 退化 ⇒ 已回退（HEAD 原样）。

**为什么没用（这次的关键收获）**：改的是**候选抽取之后**的分数——而「状+态」
在 **beam 里就已经被剪掉了**（`decode_beam_with_lattice_penalized` 的路径搜索
先按「逐词先验 + 每弧简拼惩罚」排序取 n-best），post-hoc 重打分根本看不到这条路径。
⇒ 要修这个缺口，必须改 **beam 内部的分**（路径搜索的排序目标），
这正是阶段 3「统一路径搜索 `engine/search.rs`/`scoring.rs`」的活，
而不是任何后处理补丁能替代的。四次局部尝试（⑤㉔~⑤㉚）+ 这次（⑤㊱）已经五次印证同一条边界。

## ⑤㊳ 正确的宽度实验：**宽度不是瓶颈**（结论已定）

缺口在**路径搜索本身**（哪些边会被展开、状态怎样被保留）——这正是阶段 3

⇒ 两处改动均已回退（n-best 保持 4）。

**测量纪律（第二次踩，写死在这里）**：量之前先证明**仪器在生效**——
①不能拿被 `MAX_CANDIDATES` 截断的"候选条数"当判据；②用一个已知会变的观测量
（如 `wsm` 的 #1 在关旧通道后从「为什么」变成「无生命」）做自检；③跑完再撤销量具。

## ⑤㊴ 零代码诊断：词库与混拼弧都没问题，缺口在**路径展开/保留**

对 `ztai`→状态 逐项验证（全部零代码，只用 recall_trace）：

| 输入 | 结果 | 说明 |
|---|---|---|
| `zhuang` | #1 装、**#2 状** | 「状」在词库里，key = `zhuang` |
| `tai` | #1 太、#2 台、**#3 态** | 「态」在词库里 |
| `zhuangtai` | **#1 状态** | 「状态」整串词条存在 |
| `zhuang t` | **#1 状态** | 混拼（完整音节 + 单个首字母）**能走通** |
| `ztai`（旧通道开） | #1 状态 | 旧通道直接给对 |

⇒ 词库、整串词条、混拼弧机制**都没问题**。缺口只剩一种可能：对以**单字母窗口开头**
的输入（`ztai` 的 `z` → `zhuang` 这类），剪枝把这条路径丢掉了——要么弧没展开，
要么 beam 没保住对应的状态。

**下一步的具体做法**（下次接手时一步到位）：在 `build_abbrev_lattice` 之后加一条
**临时**迹（`XWX_TRACE=1` 门控），打印格上 **位置 0** 的边（word / pinyin / freq /
是否简拼弧）；跑 `ztai` 看有没有「状 | zhuang」这条边：
- **有** ⇒ 是 beam 剪枝问题（改 `decode_beam_with_lattice_penalized` 的状态保留策略）；
- **没有** ⇒ 是弧枚举问题（`abbrev_syllables("z")` 是否含 `zhuang`，即 RIME 第三条
  `zh→z` 规则有没有真的被覆盖）。
一条迹就能把范围从"路径搜索"缩到二者之一，之后才是阶段 3 的重做。

## ⑤㊵ **决定性发现**：`ztai` 这类输入根本没建简拼格（判据写错了对象）

按 ⑤㊴ 加了临时迹（用完已撤）打印简拼格位置 0 的边——**一条都没打出来**。
再看门槛迹：

```
门槛: reachable=false tolerant_explains=true len=4 pure_abbrev=false
      covered_whole=true exact_covers_whole=false needs_abbrev=false
```

⇒ `ztai` **连简拼格都没建**。两个原因：
1. `pure_abbrev=false`：我那条判据要求「**每个**字母都能起一个音节」，
   而 `ztai` 的 `i` 是 `tai` 的**字面尾巴**（不能起音节）⇒ 判据把这类
   「单字母缩写 + 字面尾链」的输入全排除了——**而它正是缺口的主要形态**
   （ztai/ztailan/jttqzenmy/nzgsm 全是这一类）；
2. `tolerant_explains=true` 也把它挡住（旧的第二条件）。

**修正方向**（下次接手的第一步，思路已定）：
- 判据不能要求"每个字母都能起音节"，而应表达「**输入能被简拼弧 + 字面尾链覆盖**」
  ——最直接的判据就是**建格后看格子是否覆盖整串**（成本已实测 0.67~1.31ms，可接受）；
- 或者用一个便宜的**结构信号**：首窗口是单字母且**它本身不是完整音节**（`z`/`w`/`b`…），
  即"开头就是缩写"⇒ 这类输入放宽 `tolerant_explains` 那道闸。
- 之前「关掉旧通道后 20 条只剩 5 条正确」的现象，根因就在这里：大部分输入的格子
  压根没建，当然产不出读法。

**这一步把阶段 3 的入口彻底定位了**：不是 beam 剪枝、不是弧枚举、也不是排序，
而是**门槛把该建格的输入挡在门外**——一个判据问题，改动面比原先估计的小得多。

## ⑤㊶ 「开头即缩写」判据落地：`ztai` 这类输入终于会建简拼格

按 ⑤㊵ 的结论修判据。判据（都是**结构事实**，不拍阈值）：
`!reachable` + 首字母不成音节 + **前两字母**都不成音节 + 前两字母不是 `zh`/`ch`/`sh`
+ 副索引在位（`self.dict.has_abbrev()`）。命中这一支时用**合并前快照**
`exact_covers_whole` 判「是否已有整串读法」。

三个坑（都是测试/语料当场逮住的，逐个修掉）：
1. 只要求首字母不成音节 ⇒ 打错的正常输入（`nihso` 开头其实是 `ni`）也被拉进来，
   `edits` 语料 MRR 0.728 → **0.680** 退化 ⇒ 收紧为「前两字母都不成音节」；
2. 不排除 `zh`/`ch`/`sh` ⇒ 全拼输入 `zhongguor`（`zh` 是合法双字母声母）被误判，
   钉子用例 `real_dict_partial_syllable_completions_reach_the_first_page` 红
   （「中国」被挤出前 10）⇒ 显式排除三者；
3. 忘记 `has_abbrev` 约束 ⇒ 降级契约用例 `engine_without_abbrev_index_degrades_gracefully` 红
   （无副索引时纯首字母串不得有 Abbrev 候选）⇒ 与 `pure_abbrev` 同一约束。

**实测**（20 条纯缩写清单 + 四套语料 + 对拍）：
- **首位零变化**（20/20 与基线一致），**10/20** 输入候选列表变长（格子开始贡献词级候选）；
- daily 12/12·**1.000**、mixed 13/14·0.929、keystrokes 12/12·0.877、edits 6/6·0.728 **全在基线**；
- v1 对拍 44 输入 **0 变化**；clippy **0**；测试 **401 passed / 0 failed**。

⇒ 阶段 3 的"入口"这一步完成：该建格的输入现在都建了。下一步是量格子单独跑的成绩
（关旧通道 + 指标准入前 10），看缺口的真实剩余量。

## ⑤㊷ 门槛修好之后再量一次：格子单独**仍是 5/20** ⇒ 缺口确实在路径搜索/打分

仪器自检（这次做了）：`wsm` 的 #1 在开关关时是「为什么」、开时是「我是猫」⇒
`XWX_PROBE_NO_ABBREV` 确实生效，测量可信。

结果：**#1 正确 5/20、正确读法进前 10 也是 5/20**，仍缺 15 条
（zmgai/ztai/ztailan/wsm/zgr/yij/smsh/nhma/srkl/gxfc/zyaq/gzsl/jttqzenmy/zgdsq/nzgsm）。

⇒ **⑤㊶ 的门槛修复是必要的、但不是充分的**：该建格的输入现在都建格了（10/20 的候选
列表因此变长），但**正确读法仍产不出来**。所以阶段 3 的剩余缺口确实是**路径搜索与打分**
（哪些边被展开、状态如何保留、路径分怎么算）——`engine/search.rs`/`scoring.rs` 的活，
而不是门槛或弧枚举。

**留给下一步的确定事实**（不用再查）：
- 词库齐备：`zhuang`→状、`tai`→态、`zhuangtai`→状态、`zhuang t`→状态 都正常；
- 简拼弧机制正常（`zh→z` 规则、`abbrev_syllables` 含 `zhuang`）；
- 门槛正常（ztai 现在 `needs_abbrev=true`、会建格，成本 0.67~1.31ms）；
- **n-best 加宽无效**（4→16 仍 5/20）⇒ 不是"排在后面被截断"；
- ⇒ 只剩一种可能：**beam 在搜索过程中就没有把这条路径展开/保住**（`BEAM_WIDTH = 16`
  的状态保留策略，或路径分的口径让「状+态」在中途就被剪掉）。

## ⑤㊸ 又一层原因：**层序**——格子的简拼候选排在容错层之下

看 `ztai` 的格子单独候选表（旧通道关掉）：前 10 **全是 `Fuzzy`**
（摘/宅/寨/债/窄/斋/翟/爱/艾/哎，都是把 `ztai` 容错读成 `zhai`/`ai` 的结果），
`Abbrev` 层的候选排在它们**下面**（层序 Exact → Fuzzy → Abbrev 是既有设计）。

两条推论：
1. 即使简拼格产出了「状态」，它在**候选层序**里也会输给容错层的「摘」——除非它像旧通道
   那样**覆盖整串并被置顶**（`lookup.rs` 的整串候选置顶规则只作用于简拼那一支产出的
   整串候选）；我上一步加的**词级**抽取产出的候选不带整串覆盖，因此拿不到置顶、只能排在后面。
2. 所以「格子路径能不能替代旧通道」这个问题，实际包含**两个**独立条件：
   ① 产出正确读法（路径搜索/打分）；② 让它在**层序与置顶规则**里拿到应有的位置。
   旧通道赢在②——它的候选天然覆盖整串、被置顶。

**这解释了三次"加了候选但指标不动"的现象**：新候选确实进了池子，但层序在容错层之下、
又没拿到置顶，于是从不出现在前 10。

⇒ 阶段 3 要做的两件事现在都很具体：
- **路径搜索/打分**：让「状+态」这类成链读法在 beam 里被展开并保住（`BEAM_WIDTH = 16` 的
  状态保留策略 + 路径分口径）；
- **层序/置顶**：让格子产出的整串简拼读法走与旧通道**同一套**置顶与层序规则，
  而不是只有旧通道那一支能置顶。

## ⑤㊹ 决定性一查：`ztai` 的简拼格**一条候选都没产出**（不是排在后面）

做法：把 `recall_trace` 的打印上限临时提到 60（用完已撤），关掉旧通道单独看 `ztai`。

结果：候选共 60 条，**`Abbrev` 层一条都没有**（`grep Abbrev` 为空），更没有「状态」；
60 条全是容错/精确层的读法（摘/宅/寨/…）。

结合 ⑤㊶（门槛修好后 `needs_abbrev=true`、简拼格确实会建、耗时 0.67~1.31ms）可知：
**简拼格建了，但 `best_chain_candidates` 在上面找不到任何覆盖整串的路径** ⇒
「状+态」这条链在**路径搜索**里就没有成立——不是排序、不是层序、不是 n-best 截断。

⇒ 下一步只剩一个动作要点：**在 `build_abbrev_lattice` 之后打印格上位置 0 的边**
（⑤㊴ 计划过，但当时门槛没过、那一支根本没跑，所以什么都没打出来；现在这一支会跑了）：
- 若边里有「状 | zhuang」⇒ 位置 0 没问题，缺口在**链如何被接起来**（后向/beam 的转移）；
- 若没有 ⇒ 弧枚举在**首窗口**这一支没展开（`len==1` 的分支与 `lens` 的取窗口逻辑）。

这是唯一还没做的、且一步就能定性的实验。

## ⑤㊺ **机制找到了**：简拼弧只拼多音节词 ⇒ 单字词上不了链，「状+态」永远接不起来

按 ⑤㊹ 的计划打印了简拼格**位置 0** 的边（临时迹，用完已撤）。结果：

```
门槛: ... pure_abbrev=false ... needs_abbrev=true          ← 门槛修好了，格确实建了
简拼格位置0: 杂沓|za ta 杂谈|za tan 杂糖|za tang 则他|ze ta … 姿态|zi tai 字体|zi ti …
```

两条关键事实：
1. **弧枚举没问题**：位置 0 的边里 `zhuang` 出现了 **15 次**（`z`→`zhuang` 这条弧在）；
2. **位置 0 的边全是「多音节词」**（za ta / zi tai / zi ti…），**没有单字词**——
   因为 `lattice/build.rs:417` 有一条既有守卫：**简拼弧只拼多音节词**
   （理由写在注释里：一个字母配单字词等于把整串读成逐字串，`MixedDfs` 的
   `used_literal` 门槛同一口径）。

⇒ **「状」(单字,拼音 `zhuang`) 上不了简拼链** ⇒ 「状+态」这条路径在格子**根本无法形成**
⇒ `best_chain_candidates` 当然一条都产不出（⑤㊹ 的零候选由此而来）。
这与"读取/排序/n-best/层序"都无关，是**读法来源被守卫限制**。

**下一步（两个可选方向，需先想清楚再动手）**：
- **A（窄）**：允许简拼弧在**链的末尾或特定位置**接单字词（例如只允许"最后一个音节"或
  只允许 `词长 ≥ 2` 的链中间夹单字），既能表达「状+态」，又不至于退化成逐字串；
- **B（正）**：把旧通道的匹配语义（`lookup_mixed` 的 `MixedDfs`：每位要么字面音节、
  要么消耗一个首字母并把该音节剩余字母从索引枚举）**整层搬进格子**——这正是 codex
  方案里阶段 2「单缩写音节 + 字面尾链的可穷尽约束匹配」的字面内容，
  也是阶段 3 统一路径搜索的前提。
无论哪条，验收都用现成口径：20 条清单「正确读法进前 10」（当前 5/20）+ 四套语料 +
v1 对拍 + perf 同条件。

## ⑤㊻ 尝试 F（窄放宽单字）：**没打中**，回退；正确的放宽必须是**路径级**的

按 ⑤㊺ 的 A 方案试：把守卫改成
`!past_abbrev || chain.len() >= 2 || pos + len == pinyin.len()`（末窗口允许单字）。

**结果**：格子单独仍是 5/20（一条都没浮出来），四套语料不变（无退化）⇒ 已回退。

**为什么没打中**（这次的关键收获）：`past_abbrev` 对**这条弧自身**就是 true——
也就是说守卫在**位置 0 的第一个窗口**上就已经生效（`z`→`zhuang` 的「状」是单字 ⇒
`chain.len() >= 2` 不成立 ⇒ 直接拒掉），根本轮不到"末窗口"那个条件。
所以"末窗口开口子"永远救不了 `ztai` 这类输入。

**正确方向**：守卫想阻止的是**路径级**的病态形态（`wmjtqbj` → 「王莽讲堂前北京」＝
一串单字），而不是"某条弧上的词是单字"。所以放宽应当放在**路径/候选级**：
- 允许构成路径的词里有单字词，但**要求该路径至少含一个 ≥2 音节的词**
  （或等价地：单字词数 ≤ 路径词数 - 1）；
- 这样「状(单字)+态」成立（含「态」吗？两个都是单字 ⇒ 需再确认"态"是否必须 ≥2 音节——
  若两个都是单字，则该规则仍会拒绝，需改成"至少一个词 ≥2 音节 **或** 整串命中词条"）。
- 最稳的判据其实是：**整串恰好是词库条目时允许全部单字**（`zhuang tai` = 状态 ✓ 是词条），
  即"链读出来的整串有没有词条背书"——这与 ⑤㊱ 的思路一致，但必须放在**建格/搜索**里
  （那次放在候选抽取之后，路径早被剪掉了）。

## ⑤㊼ 尝试 G（剩余是完整音节 ⇒ 允许单字）：**仍无变化**，回退

在守卫上加结构判据：`tail_is_syllable`（窗口之后的剩余输入恰好是一个完整音节）时允许
简拼弧接单字词——`ztai` 的「状」应当因此放行。**实测：格子单独仍 5/20，四套语料不变** ⇒ 已回退。

**推论**：我先前"守卫是唯一堵点"的判断**不完整**。即使放行「状」这条弧，链路也没形成。
下一步不要再猜守卫，而是**直接给建格过程加一次到位的最小插桩**（一次就能看到：
哪些窗口进了 `readings`、哪些弧的 `prefix_state` 是什么、哪些词因为哪一条判据被丢），
据此定位真正的堵点。**插桩要点**（下次接手直接用）：
- 在 `readings` 组装完成后打印：`pos / len / window / readings 列表`；
- 在 `abbrev_word_len_ok` 判定处打印：`chain / past_abbrev / chain.len() / tail / 判定结果`；
- 在 `prefix_state == None` 的 `continue` 处打印被丢的 key。
这样 `ztai` 一条输入就能看出「状」到底在哪个环节消失，不用再反复假设-试探（⑤㊻、⑤㊼ 两次都
因为假设不全而空转）。

## ⑤㊽ 插桩结果（推翻 ⑤㊺/⑤㊼ 的结论）：链是通的，是**分支内的候选选择**丢了它

给建格过程插了两处最小插桩（首窗口 readings 全量 + 简拼词长判定的输入与结论），跑 `ztai`：

```
首窗口 pos=0 len=1 readings=[za ze zi zu zai zan zao zei …]      ← 37 条，zhuang 在其中
简拼词长判定: key=zhuang chain=["zhuang"] chain.len=1 past_abbrev=true => ok=false
简拼词长判定: key=zhuang tai chain=["zhuang","tai"] chain.len=2 past_abbrev=true => ok=true   ← 链通过
```

⇒ **⑤㊺ 的"守卫挡住单字"只对「词」成立，对「链」不成立**：`zhuang tai`（=状态，词库条目）
这条链 `ok=true`，边是建出来的。所以守卫不是堵点，⑤㊻/⑤㊼ 两次"放宽守卫"自然也无效
（它们改的是一个不挡路的地方）。

再看分支内的候选：**关掉旧通道后**，`简拼段前五` 全是 `Fuzzy`（摘/宅/寨/债/窄），
`Abbrev` 候选计数 = **0**。而默认（旧通道在）时前五是
`状态|freq=503366|cov=4|Abbrev|-15.7870 …`——**状态是旧通道给的**（freq 来自整串词条）。

⇒ 缺口定位在**分支内部的候选选择**：简拼格建好了（7.786ms）、该有的边也在，
但 `best_chain_candidates`（beam + n-best=4）没把它选出来，同时容错层的 Fuzzy 读法
（`ztai`→`zhai`）把前五占满。

**顺带更正一条失效证据**：⑤㊲/⑤㊳ 那次「n-best 4→16 仍是 5/20」的实验是在
**⑤㊶ 门槛修复之前**跑的——那时 `ztai` 连简拼格都没建，所以那个结论**无效**。
n-best 宽度对"现在已有格"的情形**尚未测过**，这是下一步第一个该做的实验
（关旧通道 + 4→16，量「正确读法进前 10」）。

## ⑤㊾ n-best 宽度**排除**（这次测法正确）+ 一条测量纪律

**实验**（前提这次是对的：⑤㊶ 门槛已修好、开关在上一轮已被证明有效）：
关掉旧通道 + `ABBREV_CHAIN_NBEST` 4 → 16。

**结果**：格子单独**仍是 5/20**（仍缺同样 15 条）；且 n-best=16 让 `edits` 语料
MRR **0.728 → 0.564**、首屏 5/6 → 4/6 退化 ⇒ **n-best 回退到 4**。

⇒ **宽度被正式排除**（⑤㊲/⑤㊳ 那次结论无效、这次有效）：缺口不在"排在后面被截断"，
而在**分支内 beam 的路径选择/打分**本身——`best_chain_candidates` 在
`decode_beam_with_lattice_penalized` 里，对同一条格（含 `zhuang tai`=状态 的边）
没有把这条整串路径选进候选，而容错层的 Fuzzy 读法把前五占满。

**测量纪律补一条**（第三次栽在同类问题上）：`XWX_TRACE` 的迹打在 **stderr**，
自检时**不要用 `2>/dev/null`**——我这次又把迹丢掉、导致"开关生效性"自检两个分支
都显示 0，等于没检。有效自检应当是：**看一个只可能由该开关改变的观测量**
（上一轮用的就是"简拼段前五从 状态|Abbrev 变成 摘|Fuzzy"，有效）。

## ⑤㊿ **beam 没问题**：简拼格上回出的第一条路径就是「状态」——缺口在**层序/置顶**

给 `best_chain_candidates` 的输出加了最小迹（用完已撤），跑 `ztai`：

```
[迹] beam 路径(4条): 状态=-17.487  姿态=-17.938  正太=-18.189  展台=-18.360
```

⇒ **简拼格建得对、beam 也把「状态」当成第一条路径回出来了**（分数 -17.487）。
这推翻了 ⑤㊽/⑤㊾ 里"缺口在 beam 的路径选择/打分"的推测。

那为什么关掉旧通道后前五全是 Fuzzy、看不到任何 Abbrev？两个原因（都在**排序与置顶**上）：

1. `sort_candidates` 是**按层序桶优先**、桶内再按分排：容错层（Fuzzy）的桶排在简拼层
   （Abbrev）之前，于是 `摘(64922) -18.68`、`宅 -18.76` 这些 Fuzzy 读法**先**排进来；
   它们的 `covered` 恰好也是 4（吃掉整串），而「状态」虽然**分数更高**（-17.487 > -18.676）
   却因为层序靠后而排在它们之后。
2. 分支末尾的**整串置顶**规则取的是"排序后**第一条** covered >= len 的候选"——在
   这个顺序下拿到它的是 `摘`（Fuzzy），不是「状态」（Abbrev）。旧通道之所以能赢，
   是因为它的候选**也在 Abbrev 层**，却因为层序里简拼层原本就只有它们，置顶时自然
   选中了「状态」。

⇒ **真正的两件事**（与 ⑤㊸ 的判断一致，现在有了确凿证据）：
- **① 层序**：Fuzzy 层排在 Abbrev 层之前，导致「分数更高、读法更正确」的简拼整串读法
  被压在容错读法后面；
- **② 置顶**：置顶只认"排序后的第一条整串候选"，没有比较分数，于是被层序先行决定。

**下一步的修法（具体、可测）**：让分支末尾的置顶规则在**所有覆盖整串的候选**里
挑**分数最高**的那条（而不是排序后的第一条），或者对"简拼层整串读法 vs 容错层读法"
按分数比较后决定谁置顶。验收口径现成：20 条清单「正确读法进前 10」（当前 5/20）、
四套语料、v1 对拍、perf 同条件。

## ⑤⑤① 尝试 H（置顶改按分数挑）：**打坏三个输入，已回退**

做法（按 ⑤㊿ 的修法）：把简拼分支末尾的置顶从"排序后第一条 covered>=len 的候选"
改成"所有覆盖整串的候选里**分数最高**的那条"。

**结果**：三个输入首位变错、mixed 语料退化 ⇒ 回退：

| 输入 | 改前（正确） | 改后（错） |
|---|---|---|
| `zmgai` | 怎么改 | 这么改 |
| `zgdsq` | 中国的事情 | 这个多少钱 |
| `nzgsm` | 你做过什么 | 你在搞什么 |
| mixed MRR | 0.929 | **0.893** |

（daily/keystrokes/edits 不变；20 条清单里这三个正好是"分数更高但读法更差"的形状。）

⇒ **"按分数挑"不是对的判据**。置顶规则想表达的是「把**本分支产出的**整串读法
放到首位」，而不是"全场分数最高者"——现在的 `covered >= len` 条件太宽，
在关掉旧通道时会把容错层的读法也纳入候选池（⑤㊿ 观察到的现象），
在开着旧通道时又恰好只命中旧通道的简拼候选（所以现状是对的）。

**下一步的正确方向**：把置顶条件从 `covered >= len` 收紧成
**「本分支（简拼格）产出的那条整串候选」**——即像全拼分支那样用 `sentence_keys`
（词, 音, 分 三元组）精确认领自己刚产出的候选，而不是靠"谁覆盖整串"来猜。
这样既不动默认路径（现状 20/20 正确），又能在关掉旧通道时把简拼读法顶上去。

## ⑤⑤② 尝试 I（置顶按三元组认领本分支产物）：**更糟，已回退**——由此得到关键结论

做法：照全拼分支的写法，让简拼分支的置顶**只认领本分支（简拼格）刚产出的那条整串候选**，
按 (词, 音, 分) 三元组精确匹配。

**结果**：**11/20** 输入首位变错，mixed 0.929 → **0.857**、keystrokes 0.877 → **0.835** ⇒ 回退。
（例：`srkl` 生日快乐→三人看来、`zmgk`/`zmgai` 怎么改→怎么关爱、`xnkl` 新年快乐→信念看来、
`gxfc` 恭喜发财→个性非常、`nzgsm` 你做过什么→你这个上面。）

**关键结论（本会话最重要的一条）**：**格子产出的链候选，质量本身低于旧通道的条目级候选。**
- 旧通道（`lookup_abbrev`）是**条目级**匹配：整串直接命中词库里的词条（`生日快乐`、
  `恭喜发财`、`状态` 都是词条，词频高、LM 也认识）；
- 简拼格的 beam 给的是**逐词拼出来的链**（`三人看来`、`个性非常`、`足够大石桥`），
  即便分数算得对，语义质量也差一截。

所以前几轮怀疑的"层序/置顶把对的压住了"是**次要**问题：即使把简拼链顶到首位，
**它也不是用户想要的那条**。⇒ **阶段 3 的工作重心应当是把「条目级匹配」做进格子**
（即 codex 方案阶段 2「统一词匹配」的字面内容：单缩写音节 + 字面尾链的**可穷尽约束匹配**——
用约束把"整串必须是某条词条"这类读法直接枚举出来），而不是继续调排序规则。
这一点与 ⑤㊽ 的插桩结果（`zhuang tai` 链 `ok=true`）是互补的：链能建，但链 ≠ 条目。

## ⑤⑤③ 数据判定：20 条里 **18 条是条目级命中**，只有 1 条是逐词链

用 `XWX_TRACE=1` 抓每条输入「简拼段前五」里**正确读法**的 `freq`：

| 类别 | 条数 | 例子 |
|---|---|---|
| **条目级命中**（`freq > 0`，整串直接是词库词条） | **18/20** | zmgai、ztai、ztailan、wsm、zgr、smsh、nhma、xxn、dbq、mgx、srkl、xnkl、gxfc、zyaq、gzsl、jttqzenmy、zgdsq、nzgsm |
| 逐词链（`freq = 0`） | 1/20 | wmjtqbj（我们今天去北京） |

⇒ **⑤⑤② 的结论被数据证实**：这类输入的正确答案，绝大多数是"**整串就是一条词条**"
（`生日快乐`/`新年快乐`/`恭喜发财`/`状态` 都是词条级命中），而简拼格现在只会
**逐词拼链**，拼出来的自然不是它们。

**⇒ 阶段 3 的下一步（明确、可测）**：把**条目级匹配**做进格子——
即在建简拼格时，额外枚举「整串输入按**混拼/简拼约束**展开后命中词条」的读法，
作为**一条边**（word = 词条、covered = 整串、abbrev 标记）。这就是 codex 方案里
阶段 2「单缩写音节 + 字面尾链的**可穷尽约束匹配**」的字面内容：
- 现成的匹配语义在 `lookup_mixed` 的 `MixedDfs`（每位要么消耗字面音节、要么消耗一个首字母
  并把该音节剩余字母从索引枚举）与 `lookup_abbrev`（纯首字母）；
- 目标不是"再写一遍匹配"，而是**让格子拥有它**，从而旧通道可以退场（阶段 5）。
- 验收：20 条清单「正确读法进前 10」（当前 5/20）、四套语料不得低于
  daily 12/12·1.000、mixed 13/14·0.929、keystrokes 12/12·0.877、edits 6/6·0.728、
  v1 对拍 44 输入 0 变化、clippy 0、perf 同条件不可区分。

### ⑤⑤③ 附录：把「条目级匹配」做进格子的施工配方（字段已核对）

**目标**：简拼格里多出一类**整串条目边**——「整串输入按混拼/简拼约束展开后恰好命中某条词库
条目」的读法，作为**位置 0 的一条边**。18/20 的正确答案就属于这一类（⑤⑤③ 的数据）。

**插入点**：`crates/xwx_engine/src/engine/lattice/build.rs` 的
`build_abbrev_lattice`（或它调用的 `build_lattice_with(..., abbrev=true, ...)`）在
返回前，往 `lattice[0]` 追加若干条边。

**边字段**（`LatticeEdge` 定义在 `crates/xwx_engine/src/engine/mod.rs:314`，已核对）：
```rust
LatticeEdge {
    end: pinyin.len(),          // 整串：边终点 = 输入末尾（字节位置）
    word: entry.word.clone(),   // 词条文本（如「生日快乐」）
    pinyin: entry.pinyin.clone(), // 词条拼音 key（音节空格分隔）
    freq: entry.freq,           // 静态词频（条目级命中时 > 0）
    fuzzy_penalty: 0.0,         // 精确匹配
    typo_penalty: 0.0,          // 不是打错
    edit_count: 0,
    gap: false,                 // 不是空词边
    abbrev: true,               // 走的是简拼/混拼读法（层序用）
}
```

**读法来源**（不要重写匹配，直接复用现成语义）：
- `self.dict.lookup_abbrev(pinyin)`（纯首字母，副索引）与
  `self.dict.lookup_mixed(pinyin)`（`MixedDfs`：每位要么消耗字面音节、要么消耗一个首字母
  并把该音节剩余字母从索引枚举）；
- 只取 `covered == pinyin.len()` 的结果（整串命中）；`covered` 是字节/字母长度语义，
  与边上 `end` 对应关系需按同一口径换算。

**为什么要放在建格阶段**：⑤㊽–⑤⑤② 三次排序类尝试全部失败，就是因为
"格子里根本没有这些读法"；把它们做成**边**之后，beam/排序/置顶全都自动按既有规则处理
（旧通道仍保留作回退点，两者按 (word, pinyin) 去重）。

**验收**：20 条清单「正确读法进前 10」（当前 **5/20**）+ 四套语料不得低于
daily 12/12·1.000、mixed 13/14·0.929、keystrokes 12/12·0.877、edits 6/6·0.728
+ v1 对拍 44 输入 0 变化 + clippy 0 + perf 同条件不可区分。

## ⑤⑤④ 落地：**整串条目边进简拼格**（阶段 2「可穷尽约束匹配」的第一块）

按 ⑤⑤③ 的配方实现：`build_abbrev_lattice` 在返回前往 `lattice[0]` 追加
「整串输入按简拼/混拼约束展开后恰好命中词库条目」的边（复用
`MmapDict::lookup_abbrev` + `lookup_mixed`，只取 `covered == 整串` 的结果，
标 `abbrev = true`、惩罚全 0）。旧通道保留作回退点，两者按 (词, 音) 去重。

**实测**：20 条纯缩写清单**首位零变化**（20/20 与基线一致）、**10/20** 候选列表变长
（格子开始贡献整串条目读法）；四套语料全在基线（daily 12/12·1.000、mixed 13/14·0.929、
keystrokes 12/12·0.877、edits 6/6·0.728）；v1 对拍 44 输入 **0 变化**；clippy 0；
测试 401 passed / 0 failed。

⇒ 阶段 2 的"把匹配语义做进格子"迈出第一步：**格子现在拥有整串条目读法了**。
下一步（阶段 3）：把旧通道从"出候选"降级为"只作回退点"，让这类输入改由格子供给，
再用 20 条清单「正确读法进前 10」看格子供给的质量（当前 5/20）。

## ⑤⑤⑤ 整串条目边之后的指标：**仍 5/20**——瓶颈回到**层序**（这次有干净的前提）

仪器自检（这次按纪律做，从 stderr 抓迹）：
`ztai` 的「简拼段前五」在开关关时是 `状态|freq=503366|cov=4|Abbrev|-15.7870`、
开时是 `摘|freq=64922|cov=4|Fuzzy|-18.6765` ⇒ 开关确实生效，测量可信。

指标：格子单独 **#1 正确 5/20、正确读法进前 10 也是 5/20**（仍缺同样 15 条）。

⇒ **⑤⑤④ 的整串条目边确实进了格子**（默认路径下 10/20 候选变长、首位置零变化），
但**关掉旧通道后它们仍排不进前 10**：容错层（Fuzzy）的桶排在简拼层（Abbrev）之前，
`摘 -18.676` 排在 `状态 -15.787` 前面（分数更低却因层序先到）。

**下一步的实验（比之前几次都更可能成功，因为前提变了）**：
现在简拼分支里**同时**有「整串条目级候选」（freq>0，如 状态/生日快乐）与
「逐词链候选」（freq=0，如 三人看来）。之前的尝试 I 失败，是因为它无差别地把
**链候选**顶上首位（质量差）；这次应当只把**整串条目级候选**（freq>0）顶上首位——
这正是旧通道候选的属性（条目级），所以两种供给的**质量**才可比。
判据：分支内 `abbrev_keys` 里 `freq > 0` 的那条 → 置顶；没有才退回原规则。

### ⑤⑤⑤ 附录：下一步实验的**障碍与绕法**（写下来免得白跑一趟）

原计划：在简拼分支的置顶里"只认分支内 `freq > 0` 的整串条目级候选"。**此路不通**：
`best_chain_candidates` 构造候选时写死 `freq: 0`（见 `lookup.rs` 里该函数的
`Candidate { …, freq: 0, … }`），所以**从候选本身分辨不出条目级还是逐词链**。

**正确的绕法**（下一步直接照做）：
1. 分支里先用与 ⑤⑤④ 的边**同一来源**算出"整串条目级读法的 (word, pinyin) 集合"：
   `MmapDict::lookup_abbrev(pinyin) + lookup_mixed(pinyin)`，只取 `covered == pinyin.len()`；
2. 置顶时优先认领 `(word, pinyin) ∈ 该集合` 的那条候选（用三元组里的 score 精确匹配，
   写法照全拼分支的 `sentence_keys`）；
3. 集合为空时退回现有规则（"排序后第一条 covered >= len"）。

**为什么这样比尝试 I 更可能成功**：尝试 I 认领的是分支的**全部**产物（含逐词链
`三人看来`/`个性非常` ⇒ 11/20 变错）；这次只认领**条目级**产物（`生日快乐`/`状态`，
与旧通道同类、质量可比）。

**验收（预先约定，违反即回退）**：20 条首位不退化 + 四套语料不低于
daily 1.000 / mixed 0.929 / keystrokes 0.877 / edits 0.728 + v1 对拍 44 输入 0 变化 +
clippy 0 + 测试 401 passed/0 failed。

## ⑤⑤⑥ 尝试 J（置顶认领条目级候选）：**无实测收益，已回退**——但定位到了真正的杠杆点

做法（按 ⑤⑤⑤ 附录的绕法）：在简拼分支里先算出"整串条目级读法的 (word, pinyin) 集合"
（`lookup_abbrev` + `lookup_mixed`，`covered == 整串`），置顶时优先认领集合内的候选，
集合为空才退回原规则。

**实测**：默认路径**首位零变化**、四套语料全在基线；**格子单独仍 5/20**（自检通过：
`ztai` 的简拼段前五随开关从 `状态|Abbrev` 变成 `摘|Fuzzy`）⇒ 无实测收益、且每次查询
多两次词库调用 ⇒ **已回退**。

**为什么没生效（这是本轮真正的收获）**：分支内的置顶**被后面的最终排序撤销了**——
`lookup_candidates` 尾部还有一次 `sort_candidates` + 截断（以及 `merge_with_abbrev`），
它按**层序桶**重排（容错层 Fuzzy 桶在简拼层 Abbrev 桶之前），于是刚被顶到首位的
条目级候选又被 `摘/宅/寨` 压回去。

⇒ **真正的杠杆点是最终的排序/合并口径（层序桶），不是分支内部的置顶**。
下一步应当在那里动手（例如让"整串条目级简拼读法"在层序中得到与它证据相称的位置），
而不是继续在分支内部调整置顶顺序——这一条把前面 ⑤⑤①/⑤⑤②/⑤⑤⑥ 三次失败串起来了：
**它们都改在"会被最终排序覆盖"的位置上。**

## ⑤⑤⑦ 读到排序实现：简拼进第一页的**设计通道是配额，不是排序**

`sort_candidates`（`crates/xwx_engine/src/engine/rank.rs:14`）的排序键是
**`(u_min 桶, 拼写来源层序, 分数 − 覆盖罚分, 频次降序, …)`**，其中注释明确写着：

> 同桶内层序（第二键）保持「**精确 → 模糊 → 简拼**」的结构性优先
> （防 `xx` 类上千条简拼候选冲垮全拼第一页），**简拼目标词进第一页的通道是
> 配额（`ABBREV_QUOTA`，保留），不是排序**。

⇒ **这解释了本会话一串失败尝试的共同下场**（⑤⑤① 按分数置顶、⑤⑤② 按三元组认领、
⑤⑤⑥ 认领条目级候选）：它们都在与**层序第二键**对抗，而层序是有意设计、并由
配额另外兜底的——所以任何"把简拼候选在排序里顶上去"的做法都会被这一键压回。

**下一步的正确落点（两个候选，需择一）**：
1. **配额通道**：检查 `ABBREV_QUOTA` 的实际效果——旧通道的整串条目候选之所以能进第一页，
   很可能靠的就是配额（而不是排序）；那么让**格子产出的整串条目候选**也走同一个配额通道，
   才是与设计一致的做法（而不是改排序键）。
2. 若要动排序键，必须连带处理配额的语义（否则会出现双重优待）。

**另附一个待解的观测**（下次带迹复核）：⑤⑤⑥ 的置顶认领在逻辑上应当生效
（`entry_keys` 含 `状态|zhuang tai`，而分支产物里也有 状态|zhuang tai），但指标没动。
可能的原因：认领发生时 `ranked` 里那条候选的 `(word, pinyin)` 与词条键不完全一致
（如分支产物用的是链式 key），或置顶后又被后续步骤覆盖——**加一条迹即可判定**。
