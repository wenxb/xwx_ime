## 1. 定过又推翻的判断（别再走一遍）

### ① 「A 和 B 必须一起做，否则返工」——**错的**
我最初认为 Block A（候选管线）和 Block B（输入缓冲）都要动 `lookup_candidates`，
分两次做会返工。**重读代码后不成立**：A 消费的是「格 + 后向 DP」，
B 改变的是「格里有哪些边」和「输入串形状」，B 后做不会迫使 A 重写。
真正强耦合的只在 **B 内部**（B1/B2/B3 共享输入缓冲与切分层）。

### ② 「简拼要给 SYLLABLES 加单字母音节」——**绕开了**
一度以为简拼必须让 `zgr` 能被切成 `['z','g','r']`，就得往
`segmenter.rs:SYLLABLES` 加单字母音节——而那里的注释明确说了不能加
（DP 会产生大量无意义切分）。
**最终方案绕过了这个两难**：`lookup_abbrev`/`lookup_mixed` 返回的词
**本来就覆盖整个输入串**（用户打前缀、拿到整词），所以它们是整串候选，
直接合并进候选列表即可，**根本不进 lattice**。

### ③ 「调排序那 39 个词收益最快」——**夸大了一个数量级**
按字/词拆开后：33 个是单字同音字排序差异（rime-ice 与 luna 的词频数据差别，
**去对齐 librime 不是目标**），多字词只有 6 个，其中 5 个是生僻词
（明体/钟鼓/中古/公族/终古），**真正常用又排得离谱的只有「西安」（第 18 名）**。
教训已写进记忆「判据要在测量前钉死」。

### ④ 「音节表要构建期写进 abbrev.bin（v2 格式）」——**不必要**
实测 `segmenter.rs` 的静态 `SYLLABLES` 有 410 个，词库实际用到 412 个，
差集只有 `fiao`/`tei`，反向差 0。**直接用静态表**即可，
不用引入 v2 文件格式。详见 `PLAN.md` 第三节。

### ⑤ 「按未解释输入字母数当硬首键」——**规则本身有缺陷，已推翻**
为了让混合简拼的目标词露面，我定过一条规则：排序首键 = 未解释输入字母数
（候选拼音覆盖不到的字母数）。混合简拼确实修好了（中国人 22 → 1），
**但全拼第一页被生僻组合词淹了**：`beijing` 的「被/备/北」被
「被禁锢/悲寂/背脊」顶掉，`diannao` 冒出「狄安娜/蒂安娜」，
`jinan` 冒出「进啊」这种不成词的东西。

**关键洞察：病根在度量，不在系数。** 我的第一反应是「把硬首键改成罚分、
调系数」，执行者实测 0.5/0.75/1.0/1.5/2.0 五个值，发现「被禁锢」在**任何**
系数下都稳居第 5——因为 `bei-jin-gu` 的拼音长度**确实**等于输入长度，
裸覆盖度看不出它和「被」的区别。

定稿是换度量：看**剩下的字母还能不能精确切分成音节**（`u_min` 分桶）。
「中国人」之于 `zhongguor` 剩下的能切完 → 0 桶；「被禁锢」把 `jing` 拆成
`jin`+`gu` → 沉底。换了度量之后，A（全拼第一页）和 B（简拼露面）立刻同解。

> **这条是我的判断失误**：执行者按我写的规则精确实现了，也报告了
> 「单字想上屏要多翻一点，这是本规则的刻意取舍」——是我没预见到
> 「0 键生僻组合词淹没高频单字」的规模就签了字。

### ⑥ 「西安第 18 名是 A3 后向 DP 近似丢了 bigram」——**归因是错的**
这条错误归因在 `PLAN.md` 里挂了很久。实测推翻：`xian` 本身是合法音节，
「西安」与「先/现/线」**都覆盖整串**、后缀补全分**都是 0**，
A3 的后向 DP 对它们不产生任何区分。

真因是 `wanxiang.rs` 的 `score_word()` 空上下文早退返回
`floor_log10()`（≈ -11.6058，**与候选词无关的常数**），于是
**空上下文时排序 100% 由词频决定，LM 完全不参与**。
这个事实的影响面远大于「西安」——**输入法里绝大多数上屏都从空上下文开始，
也就是说每次输入的第一个词都是纯词频排序**。

旁证：`nimen`→你们 第 1、`jinan` 前 6 全是双字词，
说明 bigram 缺失根本不足以让双字词沉底。真正的分界是
**「整串是否恰好是一个合法单音节」**——是的话，覆盖整串的高频单字边
会和多字词同槽同补全（都是 0），退化成纯比词频。

### ⑦ 「空上下文查 unigram 就能修好」——**结构性走不通，别再试**
详细反例见 `PLAN.md` 第四节。一句话：**万象 gram 的值不跨键长可比**
——单字条目根本不存在（窗口模型最小 2 字），长命中键的 ln 随键长单调涨，
所以「狄安娜」(13.81) 会骑到「西安」(11.21) 头上。
实测四个参数版本全部在既有哨兵上出血，已完整回退。

### ⑧ 「A1 已经修完了」——**只修了一半**
Block A 的 A1「候选只能起始于位置 0」当初**只修了格（lattice）路径**，
`fallback_candidates` 里同样的 `for syllable in seg` 漏了。
后果是 `zhongguor` 前 20 名有 13 个只覆盖非起始音节的字。
**混合简拼打不出字，根子在这**——绕了两轮（配额、残余字母联想）才挖到。
那两轮的改动本身没错、也都保留至今，但都没打在要害上。

### ⑨ 「这个功能已经做完了」——**文档打勾 ≠ 二进制里有**（2026-10-01）

一次外部审查发现**三处**同一类病：测试全绿、文档打勾、用户却用不到或反受害。
这是本项目最该警惕的一类缺陷——**它不会让任何测试变红**。

**① 模糊拼音在生产里是死代码。**
`fuzzy_enabled` 只在 `lib.rs` 定义 / 初始化 false / 一处分发，
**其余全部在测试里**（测试自己置 true）。`main.rs` 从不设置它，
没有配置入口——而 `README.md` 早已打勾「模糊拼音 ✅」。

> **教训：`grep` 一个配置字段的「赋值点」，比读它的测试更能判断功能是否可达。**
> 测试里绿的是「能力」，不是「接线」。凡有开关的字段，都要 grep
> 进程入口里**有没有人真的打开它**。
> 已接线成 `XWX_FUZZY`（默认关闭，实测依据见 `PLAN.md` 2026-10-01 节）。

**② 造词把「连续打字」粘成句子词条。** 证据在真实用户数据里：
`~/.local/share/xwx/user_bigram.txt` 躺着 `当前主线以及已经完了是吧进度`
这种 11 字句子。根因是判据只数片段个数，不管片段**是什么**。

> **教训：用户数据文件是最诚实的需求文档。** 我们有一堆造词测试
> （单次完整词不重复造、跨标点不造、跨焦点不造）——全都绿，
> 但没有一条覆盖「用户连续正常打字」这个最高频场景。
> **测试覆盖的是我们想到的场景，用户数据反映的是真实发生的场景。**

**③ README 落后 PLAN 一个数量级。** 旧 TODO 六条里五条早做完了却挂着
未打勾；模糊拼音反过来——打着 `[x]` 但生产里无法启用。对外表述**又少又错**。

> **教训：能力 / 文档 / 生产三者要定期对账。** 判据会腐烂（第 3 节），
> 文档也会——而且更隐蔽，因为它不参与任何自动化检查。

### ⑩ 「空上下文排序 100% 由词频决定」——**对通用层成立，对用户层不成立**（2026-10-01）

`PLAN.md` 第四节那句结论需要收窄。实测（`examples/lm_ctx_probe.rs`）：
空上下文下万象对**任何**词返回同一个常数 `-11.605767`
（「西安/先/闲/狄安娜/中国/的/**龘**」七词逐位相同，连词库里不存在的字都一样）。
**但**生产进程挂了用户层，`UserLmSnapshot::log10_prob` 在无 `prev` 时
回落 unigram 计数——**用户用过的词在句首是可区分的**。

> **教训：「LM 不参与」这类结论要先问「哪一个 LM」。**
> 引擎是 `LmStore` 枚举聚合（Bigram / Wanxiang / Mixed），
> 只看 `wanxiang.rs` 就下结论会漏掉用户层。
> 这同时划清了「空上下文 unigram backoff 被否决」的**边界**：
> 被否决的是**通用 gram**（值不跨键长可比），
> 用户层 unigram 是可比的自然数——将来再动空上下文，别把它一起砍了。

### ⑪ 移植一个组件前，先确认它挂在**哪条链**上（2026-10-01）

`MAX_COIN_CHARS` 的原注释称它「对应 librime `unity_table_encoder` 的长度上限」。
实读 `/usr/include/rime/gear/unity_table_encoder.h` 后确认**溯源是错的**：
`UnityTableEncoder` 是 **`table_translator`（码表）**的组件，
而拼音走的是 **`script_translator`**——后者根本没有 encoder
（这一点 `gear-audit.md` 第 3 节其实早就写明了）。

> **教训：`gear-audit.md` 这类清单要连「挂在哪个 translator 下」一起读。**
> librime 有多个 translator（table / script / reverse_lookup…），
> 组件清单是**按 translator 分组**的。只对着组件名找对应关系，
> 就会把码表的特性搬到拼音引擎上。
> 24 这个数值本身仍合理（覆盖人名/诗句），保留；但理由要换掉。

### ⑫ 测试设施自己会撒谎：一次集成层「全绿」的六重假象（2026-10-01）

根 `tests/` 的 D-Bus 集成层交付时声称「7 passed」，实际是**大部分红、
部分永久挂起**（一次跑了 15 分钟不返回，还漏了 4 个孤儿引擎 + 4 个孤儿
bus）。逐条挖出**六个缺陷，全部在测试设施里**，引擎侧无罪。这六条是同一
类病的六个面：**测试没在测它声称测的东西**。

1. **信号 100% 被静默丢弃**。监控线程用
   `Body::deserialize::<OwnedValue>()`；每个 IBus 信号体都是**多字段结构**
   （`UpdatePreeditText` = `(vubu)`），`OwnedValue` 只接受单值 → 反序列化必失败
   → `continue` 丢掉 → 所有断言报 `已见: []`。**测试红了却指向引擎，
   而引擎一直在正确发信号。** 改 `deserialize::<Structure>()`。
   > 教训：**`let Ok(..) = ... else { continue }` 是最危险的写法**——
   > 它把「解析失败」和「没有信号」变成同一种可观测结果。凡是静默 `continue`
   > 都要能报数。

2. **变体没拆**。IBus 把对象藏在 variant 里：体是 `(v u b u)`，第 0 个字段
   是 `v` 包着 `IBusText`。访问器却按「体就是 IBusText」读第 2 个字段
   → 读到 `Bool(true)` → 文本恒为 `None`。拆包后，**测试原本断言的
   `(sa{sv}sv)` / `(sa{sv}uubbiavav)` 恰好是内层签名**——断言其实是对的，
   错的是解码层。

3. **空体信号被丢**。`HidePreeditText()` / `HideLookupTable()` 的体是空，
   结构反序列化失败 → 又被 `continue` 丢掉 →「Esc 后必须发 Hide」永远红。

4. **方法调用没有超时**。`zbus` 阻塞式 `call_method` 自身**无超时**：引擎一旦
   不应答，调用就停在 `epoll_wait(-1)`，测试线程永不返回，整个套件挂死
   （strace 抓到：主线程在 `futex` join 一个卡死的测试线程，那个线程在
   `epoll_wait(..., -1)`）。改成 worker 线程 + `recv_timeout` 后，
   **挂起变成一条点名方法的失败**——套件从「永不结束」变成 13 秒跑完。

5. **监控器是懒创建的**。`ensure_monitor()` 原本只在第一次 `settle`/`drain`
   时调用。测试若**先打字、后 settle**，信号在 match rule 注册前就发完了
   → 收到空批次 → 却报「没有候选窗」。改为 `start_engine` 里**先监听再放行**。

6. **静默期太短的假等待**。多处 `settle(60ms, ..)` 靠「安静 60ms」判定收集
   结束——负载下信号晚到就被截断。改成 `wait_signal("UpdateLookupTable", ..)`
   **等指定的那一个**。注意 `clear_backlog()` **同时会 drain 信号通道**，
   所以它必须**在动作之前**调用；放在动作之后会把你正要等的信号冲掉。

> **总教训**：一个「全绿」的测试套件，只有在**它有能力变红**时才值钱。
> 这六条里有五条的表现是**红/挂**，但都指向了错误的方向（引擎），
> 真正的问题是断言根本没接上被观测的信号。**先证明测试能看到东西
> （`已见: [...]` 非空），再谈它断言得对不对。**

### ⑬ 引擎真 bug：先占名字、后挂对象（2026-10-01）

集成层唯一挖到的**引擎**缺陷，而且是对的：`src/main.rs` 原本先
`conn.request_name(ENGINE_SERVICE)`，**之后**才
`object_server().at(FACTORY_PATH/ENGINE_PATH)`。于是存在一个窗口：
**名字已可见、路径还没人应答**——此刻到达的方法调用永远不会返回。
实测形态：`FocusOut` 10s 无应答，而引擎进程 `/proc` 状态是 `S`（活着）、
日志干净（启动完成），即**活着但不分发**。

修法：**先 `at()` 挂对象，再 `request_name`**——「名字可见」就必须
「即可服务」。这是 D-Bus 的标准做法，不是绕行。

> 教训：**`request_name` 是「发布」，发布之前必须先能履约。**
> 这类窗口在单测里永远看不见（单测直接调库函数，不过总线），
> 只有真正跨 D-Bus 边界的测试才抓得到——这正是集成层存在的理由。
> 测试侧同时加了 `Peer.Ping` 就绪探针（`zbus` 自己应答，
> 比 `GetNameOwner` 更能证明「对象已在分发」），两层保险。

### ⑭ 用户层给「没学过」的词发**绝对**中性分 = 学习反而降权（2026-10-02）

用户报「纯简拼 `ky` 里『可以』不在前面」（`可以` 词频 505814，是 `ky` 全桶
最高）。根因**不在简拼算法**，在 `MixedLM::score`：用户层对没有证据的词
发一个**绝对**中性分（`NEUTRAL_LOG_PROB = -1.0`），而用户层自己的概率是按
**用户语料规模**归一化的——真实 `~/.local/share/xwx/user_bigram.txt`
（Σc+vocab ≈ 175）下，计数 1 ≈ ‑1.94、计数 3 ≈ ‑1.64，**全在中性分之下**。
于是学过的「可以」被压到第 **11** 名，从没学过的「跨越/可用」白拿 ‑1.15。

> **教训：跨模型混合时，绝不能用一个绝对常数当「不表态」票。**
> 两层量纲不同（一个按通用语料，一个按用户自己的几十条计数），
> 这个常数落在哪一侧完全取决于用户打了多少字——用户用得越多，
> 结论越会翻转。正确口径是 **backoff**：没证据 ⇒ 原样输出通用层分
> （没学过的词逐位不变）；有证据 ⇒ 概率域插值，且结果
> `.max(base)`——**学习永不降权**（计数只有正证据，负证据是
> Ctrl+Delete 的屏蔽表）。
> 附带挖出一条同类：`coin_entry` 只 `add_entry` 不 `learn`，
> 自造词「查得到但排不上」（旧断言是**靠中性分**偶然排到第 1 的），
> 已补上计数——`user_lm.rs` 的 `entries` 注释本来就写着
> 「召回与打分两条通道一体」。

### ⑮ 跨模型混合：绝对概率常数会随语料规模漂移，**计数才是不变量**（2026-10-02）

用户追问「选错一次会不会一直错下去」时查出的三条实测事实：

1. **一次误选永久置顶**：`xian` 误选「闲」1 次 → 第 1（初始第 10）；随后连
   选对「先」3 次 →「先」回第 1，但「闲」稳居第 2，只能 Ctrl+Delete 清。
2. **个人加分随语料规模衰减**：同一句「学 1 次目标词」，往用户表里灌
   0/200/2000/10000 条无关语料后，加分 +11.45 → +9.15 → +8.15 → **+7.45**
   ——重度用户的个人化比新用户弱 4 个数量级。
3. **断崖而非梯度**：学过 vs 没学过差 ~9 个数量级，而学 1 次 vs 3 次只差 0.2。

> **教训：跨层混合时，两个量纲「可不可比」看分母，不看形式。**
> 用户层概率的分母是**用户自己的语料规模**，通用层是全民语料——把它们送进
> 同一个 logsumexp 做插值，等于假设两者可比，而这个假设会随用户打字量漂移
> （第 2 条）。可用的不变量是**计数**：它不依赖任何分母，换算出多少加分由
> 单一常数 [`USER_COUNT_GAIN_R`](../crates/xwx_engine/src/lm.rs) 决定。
> 改后的口径 `score = base + log10(1 + c·R)` 同时给出三条性质：无证据不动
> 通用层（c=0 ⇒ +0，逐位相同）、学习永不降权（加分 ≥ 0）、与语料规模无关
> （由 `mixed_boost_independent_of_corpus_size` 钉住）。
>
> 附带一条**语义反转**：Ctrl+Delete 过去刻意**不动**计数（理由「删候选 ≠
> 抹掉频次」），现在改成**连计数一起清**。原因是屏蔽键是 `(拼音, 词)` 而计数
> 按**词**记——只屏蔽的话，同一个词在别的拼音路径上照样带着计数被加分
> （多音字串味），用户看到「删了它，换个打法又冒出来还更靠前」。计数就是
> 排名的燃料，燃料不清等于没删。
>
> **标定方法（可复用）**：判据先钉死，再 sweep。先测候选分差只有两档
> ——同类词 vs 词 **0.002~3.70**，「逐字拆解 vs 整词」**10.1~14.7**——再拿
> `R ∈ {10,30,100,300,1000}` 扫「误选 #2/#5/#10 一次后落第几」，取
> **R=1000**（一次 +3.0 覆盖全部同类竞争；结构墙要 5×10¹⁰ 次才翻得过去）。

### ⑯ 「够了就停」= 隐式排序：收集期的早停是拿探索顺序当质量（2026-10-02）

`meiy` 打不出「没有」——**不是排序问题，是根本没召回**。DFS 收集期「收满
500 条就停」，而这 500 条按**探索顺序**先到先得（`mei y*` 下几百个 key，
`mei you` 还没轮到名额已被 `mei yi*` 占满）；**截断发生在排序之前**，
所以「按词频取前 N」根本没有机会生效。铁证：列表第 1 名「每一个」词频
500354，缺席的「没有」是 **504685**。

> **教训一：任何「够了就停」都是隐式排序**——它用探索顺序（= 代码结构、
> 字节序、循环次序）替代了打分。质量决策只能发生在**排序之后**。
>
> **教训二：成本问题先打桩量清「钱花在哪」，别猜。** 我先猜是「收词条太多」，
> 加了每 key 额度，实测 4/8/32 **毫无差别**（都是 3.8ms）；打桩才知道真正的
> 成本是 **DFS 探索本身**（20_000 步预算 × 每步一次二分迭代 ≈ 3.8ms）。
> 猜错方向会白改一轮。
>
> **修法与成本三件套**（判据先钉死再标定）：
> 1. 收集期不做决策 + 排序后 `truncate(500)` 按词频截断；
> 2. **探索上界** `MAX_MIXED_COLLECT = 8 × 500`：取消上界 → `zhongg`
>    0.343ms → 4.13ms（破 5ms 门槛）；上界 4000 → **2.80ms**；
> 3. **整 key 跳过**（精确分支界限）：词块内 freq 降序 ⇒ 「该 key 最高词频
>    < 收集池第 N 名的下界」就整 key 跳，一条都进不了最终列表。前提
>    「组内 freq 降序」经抽样验证（含「一」130 条）。
> 4. 索引预算 `MAX_MIXED_DFS_STEPS` **不动**——实测收紧到 6000 会把
>    `nhao` 的 14 条召回砍到 4 条：**用召回换速度是亏的**。
>
> **教训三：回归锉会锉住「假象」。** `mixed_abbrev_targets_are_visible` 里
> 「`nih`→你好 ≤ 2」是按**当时不完整的召回列表**标定的：新召回补进来的
> 「你会」(-15.836)/「你回」(-15.878) 词频本来就高于「你好」(-15.967)。
> 修好召回后它落到第 4。按项目规矩**逐条说明后**把上限改成 4（旧列表里的
> 你还/你和/你很 一条没掉，不是排序退化）。

### ⑰ 「整串是合法全拼」≠「用户打完了」；新能力会让旧断言假失败（2026-10-02）

T2（末尾半音节）踩到三件事：

> **一、同一个「末尾半个音节」有两种形态，必须都覆盖。**
> 尾巴不构成音节（`zho`→zhong）走 DFS 那条路；尾巴**碰巧是合法音节**
> （`niha` 的 `ha`、`beijin` 的 `jin`）会被判成「整串合法全拼」走精确匹配。
> 只在 DFS 那一条路上加半音节读法 → `niha`/`beijin`/`meiyo` **全漏**。
> 教训：**给查询加一种「读法」时，先数清入口有几条，读法要对每条都生效**
> ——所以两条路的结果要并进**同一个收集池**。
>
> **二、按能力切分，别把相邻能力顺手做进去。** 整串是全拼时，「`p = 0`」
> 的含义会从「末尾半截」变成**「音节前缀补全」**（`xian` → 整个 `xiang*`
> 区间）：那是另一个能力，实测端到端 3.10ms → **7.63ms**、候选列表从 100
> 条级别涨到满额。用「整串是否合法全拼」把两者切开后，四个目标形态一个不丢，
> 延迟回到 3.78ms。**范围边界要用测量来定，不要用直觉。**
>
> **三、测试会编码「旧能力的边界」，新能力会让它假失败。** 两条既有断言
> 在 T2 之后变红，都不是 bug：`engine_without_abbrev_index_degrades_gracefully`
> 断言「无副索引 ⇒ 零简拼层」（半音节读法走主索引，不再成立）、
> `abbrev_quota_is_floor_not_cap` 断言「`zhongguo` 不应有简拼层」（整串全拼
> 也会有末尾补全）。按项目规矩**逐条说明原断言/新断言/为什么新行为对**之后
> 改掉：前者改断**纯首字母串**（副索引真正的职责），后者改断
> **前 10 名仍是精确层**（配额不挤占精确层）。```
>
> 已知代价（未做）：半音节补全的名次偏后（#26~#49）。句首空上下文只有词频，
> 而这些词还有**整个音节没打**（`zho` 只覆盖「中」的一半，中国还有一个 `guo`）
> ——要提前就得给「未输入的音节」加罚分（A3 补全罚分的同构做法）。

### ⑱ 开发/验证环境：三件踩过的事（2026-10-02）

> **一、`just dev` 的顺序不能反：先确保 daemon 在跑，再让出引擎位。**
> 一个总线名只能一个 owner。daemon 不存在时，调试引擎会**自己拉起 daemon**，
> 而那个 daemon 一启动就按 component XML 激活 release 引擎抢走
> `org.freedesktop.IBus.Engine.xwx` —— recipe 里那 0.5 秒「让位窗口」因此完全
> 失效，**第一次 dev 必报 NameTaken**。daemon 已存在时它不会立刻回拉（实测 5 轮
> 窗口安全），所以正确顺序是：`if ! pgrep -x ibus-daemon; then ibus-daemon -rdx;
> sleep 2; fi` → 杀掉引擎 → sleep 0.5 → exec。两个场景都实测过。
>
> **二、开发期用户模型要隔离。** `just dev` 起的调试引擎原先读写真实
> `user_bigram.txt`（计数 / 造词 / Ctrl+Delete 屏蔽表三段同文件，污染后很难清）。
> 现在 debug 构建默认走 `user_bigram.dev.txt`（`user_lm_file_name()`），
> 优先级 `XWX_USER_LM_PATH` > debug 默认 > release 默认；`just install` 装的是
> release，实机不受影响。
>
> **三、别用「真实二进制 + 改过的 `XDG_DATA_HOME`」做验证。** 我这么干过一次：
> 它找不到 IBus 总线地址 → **自己拉起 daemon** → 那个 daemon 带着被删掉的临时
> 数据目录，按 XML 拉起的引擎**找不到词库**，把当时正在用的输入法弄坏了几秒。
> 要验证就走集成测试那套**私有总线**，或者干脆别跑真实二进制。
>
> 附带一条探针陷阱：`ProcessKeyEvent` 的签名是 `(keyval, keycode, state)`，
> 参数错位（keyval 传 0）会得到 `(false,)` 的假象，看着像「英文模式」。

### ⑲ ü 的匹配口径必须全层共享；简拼要「一字一字母」（2026-10-02）

> **一、一个词的名次取决于「哪个层看见它」。** 词库把 ü 写成 `v`（`lve`/`nve`），
> 用户按 `lue`/`nue` 打——`hulue` 打不出「忽略」、`lue` 打不出「略」、
> `nuedai` 打不出「虐待」。规则只有一条（`lue`→`lve`、`nue`→`nve`），但**落在
> 三处**，漏一处就残：
> 1. `segmenter::canonical_syllable` —— 唯一口径，`Segmenter::is_syllable`/`segment`
>    都走它，且**切分结果里放规范写法**；
> 2. `dict.rs::syllable_matches` —— `is_full_pinyin`/`partial_tail_readings`/
>    `segment_prefix`/`segment_input`/`MixedDfs::dfs` **五处共用**，别各写一份；
> 3. `lib.rs::build_lattice` —— **推进链里必须放规范写法**，因为 `chain.join(" ")`
>    就是查词库的 key。
>
> 第 3 处漏掉的代价最直观：候选构造完全正确，但格子拼出的 key 是 `hu lue`（查不到），
> 于是只能从简拼层兜底进来 —— 层序从 `Exact` 变 `Abbrev`，同一个词、同一个分数，
> 名次 **#1 → #59**。**「候选对了」不等于「排序也认」：要看 `spelling` 层序。**
>
> **口径（用户拍板）**：只认 üe 这一组；`lu`/`nu` 是「路/努」的合法全拼，
> **不**当 `lv`/`nv`（否则打 `nu` 会混进「女」，打 `lu` 混进「绿」）。
>
> **二、一字一字母：简拼候选的字数不得超过输入字母数。** 用户报「`wsm` 出现四个字」。
> 三个来源都要堵，少一个都漏：
> - 副索引 `lookup_abbrev`：按 key 前缀匹配，`wsm` 命中 `wsmy`（为什么要）；
> - `MixedDfs::collect` 的末位声母分支：`wei shen m` 是**字节前缀**，
>   `wei shen me yao` 也满足「以它开头」；
> - `fallback_candidates` 的前缀联想：`zho` 捞出 `zhong a guan xi`（中阿关系）。
>
> 判据用**候选全拼的音节数**，不用 key 长度（key 里 `zh`/`ch`/`sh` 可能两字母一个
> 音节）。实测 `wsm` 100 条里 78 条超长、`zgr` 83 条、副索引 `wsm` 356 条里 276 条
> 超长；修完全部归零。**只在这三层过滤**：用户 LM 里学过的词不在此列——那是用户
> 自己显式教的，不该被规则抹掉。
>
> 代价（用户已确认接受）：短输入的候选变少（打 `w` 只剩单字，不再有 我们/为什么），
> 全拼与 `nhao`/`meiy`/`women`/`diannao` 这类既有简拼输入的前 10 一条没动。

## 2. 已知的「刻意代价」（不是 bug，别去"修"）

### A3 后向 DP 的 LM 近似
候选打分用后向 DP 算「从 edge.end 到串尾的最优补全分」，
但 **LM 是左到右的**，后向拿不到精确 LM 状态，每条边只能从「无上文」起评
（bigram 下等价于只拿 unigram 分）。

**已知后果**：`xian` 的「西安」排第 18 名——双音节词拿不到 bigram 增益，
竞争不过高频单字。测试 `whole_path_beam_beats_greedy` 的断言
（`nimen` 首选从「泥」变「你」）也是这个近似的直接体现。

**为什么接受**：它只影响候选**之间**的相对排序，不影响 beam 选出的整句首选
（后者走前向精确 LM）。消除它只能回到「从 beam 幸存路径反查」
（=回到被 `BEAM_WIDTH` 钳死的老路）或引入双向 LM，都不值得。

代码注释在 `lib.rs` 的 `backward_completion` 函数级文档里，写得比这里详细。

### 回声候选的语义
照搬 librime `echo_translator`：**仅当全场一个候选都没有时才冒头**，
不是「总在末尾追加兜底项」。上屏时**不学习**（`c.echo` 时给
`learn_committed` 传 `None`），否则用户每打一次打不出字的乱码串，
引擎就学一个垃圾"词"。

### `fiao`/`tei` 不支持混合简拼切分
刻意不加进 `segmenter::SYLLABLES`——那是主切分路径，动它影响全拼行为。

## 3. 验收指标的坑

### `TOP1_AGREE` **不能**当验收门槛
两边词库/LM 不同（我们 rime-ice，librime 用 luna + 八股文 essay.txt），
对齐它等于让实现去迎合对照方的词库。只作参考。

### `NCAND_RATIO` **不能**当门槛
`MAX_CANDIDATES = 100` 截断我方候选，而 librime 的 `guo` 有 336、`shi` 有 351，
比例天花板只有 ~0.3，追它是徒劳。只用于观察趋势。

### `ZERO_ONLY_XWX` 12 → 0 是**症状**修好，不是**能力**
回声候选只让用户看见自己敲了什么、知道按空格能上屏。
简拼真正打出字要等 B3 集成完。别看着这个 0 以为简拼好了。

### `TOP1_AGREE` 只看第 1 名，**盖不住第 2~10 名整体换血**
我拿「全拼四组 `TOP1_AGREE` 不许退化」当过硬门槛，结果裸覆盖度那轮
`beijing` 的前 10 从「被 备 北 背 呗 杯」变成「被禁锢 被禁 北进 北极
悲寂 背脊」，而 `TOP1_AGREE` **一点都没动**——第 1 名一直是「北京」。

**教训**：聚合指标选错了观测点，比没有指标更危险（它会给你虚假的安全感）。
后来的判据直接点名「哪些高频单字必须在前 10、哪些生僻词不得在前 10」，
不再依赖聚合数。**能点名就点名，别让聚合指标替你判断。**

### 断言要钉「该消失的消失了」，不是「想要的存在」
`'` 分隔符出过一个**测试全绿但功能完全没生效**的 bug。
实现是 `pinyin.replace('\'', "")` 把 `'` 删掉再建格——删完就是 `xian`，
而 `xian` 本身是合法音节，`[xian]` 那条切法原样复活，
`xi'an` 与 `xian` 的候选列表**逐字节一样**。

测试没挡住，是因为它断言的是「西安**出现在**候选里」——
可西安在 `xian` 下本来就出现（第 18 名），**bug 存在时这条也是绿的**。

**消歧的定义是「另一种切法的候选消失」**（「先/现/显/线」不该在），
不是「想要的候选存在」。改成钉这个之后，把实现临时改回旧写法，
测试立刻变红。

> 这和「`TOP1_AGREE` 盖不住第 2~10 名换血」是同一类病：
> **观测点选在了不会因 bug 而变化的位置上**。
> 写断言前先问一句：这条断言在功能坏掉时会红吗？

### 交互功能要有「逐字符敲一遍」的端到端测试
recognizer 初版交付时单键断言全绿（覆盖了 `www.` 和邮箱），但真实序列是坏的：

```
❌ http://x.com  → "http:、、xcom"   ← / 被映射成顿号
❌ mailto:a@b.c  → "买:a@b.c"       ← mailto 被当拼音上屏
```

**比不做 recognizer 还糟。** 单键测试测不出来，因为没有一条跑完整个序列。

形状是这样（表驱动，`session.rs` 的
`recognized_samples_end_to_end_commit_identity`）：
**对每个字符调 `handle`，末尾 Enter，把所有 `Commit` 输出拼起来，断言等于原串。**
它在初版实现下当场复现了上面的坏结果。

> 凡是「按键序列 → 上屏文本」的功能（标点、大写、翻页、分隔符、识别）
> 都该有这么一条。单键断言只能证明每一步的局部行为，
> 证不了**整条路径**走下来是对的。

### 玩具词库测不出 mmap 的顺序问题（同一 trait，两个实现顺序语义不同）
- `SqliteDict::lookup_prefix` 按 **freq 降序**返回
- `MmapDict::lookup_prefix` 按 **字节序**返回

「声母前缀被字典序锁死」那个 bug 只在 mmap 上存在。执行者第一次做负向控制
（关掉修复看测试是否变红）时，玩具词库照样绿——因为 `SqliteDict` 本来就按
词频排，复现不了字节序偏置。

**教训**：涉及「返回顺序」的问题，玩具词库无效，必须用 `data/dict.bin`
写 `real_*` 测试。或者把断言换成只有修复路径才产生的观测量
（那轮最后断的是「逐音节配额限流」）。

> 这个顺序语义差异本身也是个坑，本轮没动它（改它超出范围），但记在这里。

### 新写的测试，要先证明它能失败
承上：怀疑一条测试是否有效时，**把实现临时改回坏的写法，确认它变红，再改回来**。
这轮就是这么验的（两条消歧测试变红、其余 apostrophe 测试保持绿，
说明观测点选对了且没有误伤）。成本几分钟，换的是「这条测试值不值得信」。

### 判据本身会腐烂，要定期重验
两次教训同构：
- `TOP10_OVERLAP` 的标签在深度 10→100 后失效，门槛「≥6.83」写的是
  一个已经不存在的单位；
- clippy「基线 6 处」清单随版本失效（`dict.rs` 三处在新版本下不再报），
  执行者无法判断自己有没有新增。

**解药**：判据要么写成不会过期的形式（clippy 已清零 → 门槛变成
「必须全绿」一句话），要么在文档里显式标注口径和测量日期。

### 延迟必须用 `--release` 测
debug 构建下同一份代码是 9.6ms 量级，release 是 1.5ms。
曾有执行者用 debug 测出「退化 7 倍」，换 release 后对上基线。
`lookup_bench` / `abbrev_bench` 一律加 `--release`。

### 验收线要按**职责范围**画，不能按 overall
我犯过：给 Block A 画了「overall `TOP10_OVERLAP` ≥ 6.0」，
但 Block A 只管 9 组里的 4 组，另外那些零分组（简拼/混合简拼/纯字母）
结构上就不可能靠 Block A 改善。**Block A 按其真实职责是达标的**
（四组均值 4.95 → 6.83），是我的门槛画错了。

### `TOP10_OVERLAP` 算的**不是** top-10 交集
`compare.py:169` 是 `len(set(rime_cands) & set(xwx_cands))`——两边**完整列表**
（各上限 100）的交集。打印的标签 `mean |rime_top10 ∩ xwx_top10|` 是陈旧的：
当初把双侧深度 10→100 时改了深度，没改指标名和标签。

**踩过的坑**：`PLAN.md` 里「全拼四组 ≥6.83 不许退化」这条硬门槛是深度 10
时代的数，我照抄进任务书，而执行者量出来是 22.90——同名不同单位，
门槛根本判不了真伪。**判退化不要比绝对值**，要拿改动前后的 probe 输出
跑同一个 oracle 做逐位对比。

### 解读 `RECALL_MISS` 要记得两个截断
`MAX_CANDIDATES = 100`（`lib.rs:61`）、`MAX_LOOKUP_RESULTS = 500`（`dict.rs:27`）。
本轮有 14 个输入的 NCAND 恰好 =100，即被截断。

### 判断「词库真没这个词」的方法与其局限
```bash
# 在 dict.bin 里搜 长度前缀 + UTF-8 词
grep -a -c -P '\x06西安' data/dict.bin
```
**局限**：这只证明词存在，**不证明它挂在匹配的拼音键上**。
我用它算过一个「上界 8.56」去反驳子 agent 的结论，后来发现界太松——
那 11 个「词库有却没召回」的词（蜗/肋/垃/偿/榜）读音根本不是那个输入。
更严谨的做法是解析 `dict.bin` 的 key→词条结构再判断。

## 5. 协作方式：什么有效

### 有效的做法
- **判据写进任务书再派活**，包括「X < 5ms 要有实测数字，不接受『应该更快』这类论证」
- **明确写「达不到就如实报，但调整标准是我的事、不是你的事」**——
  防止执行者为了凑指标去改设计或动常量
- **允许改测试断言，但必须逐条说明「原来断言什么/改成什么/为什么新行为对」**，
  不许删除或改名。Block A 那三处改动因此可复核，且断言是**加强**不是放宽
- **禁止越界**：「本任务只做存储层，不要接进 lib.rs」——出问题时定位范围小一半
- **子 agent 的报告必须自己复核**：本轮实际抓到过「把推测写成事实」
  （根目录 installation.yaml 的时间归因）和「结论对但举例错」
  （说中古/钟鼓不在词库里，实际在）

### 并行派活：文件所有权要写死
标点与排序两轮是并行跑的，任务书里各自列明「你独占哪些文件、
绝对不要碰哪些」。踩到并避开的两个坑：

- **测试总数会互相干扰**。两边都新增测试，谁看总数都对不上基线。
  判据要写成「**0 failed + 既有测试一个不许少**」，并明说
  「总数对不上不要惊慌，不要去改别人的测试」——否则很可能有一方
  看到数字不对就去动对方的断言。
- **probe 输出会被对方污染**。标点那轮如果跑对拍自证，会看到候选列表变了，
  那是排序 agent 干的。任务书要写「先判断是不是对方造成的，
  别把对方的改动记到自己账上」。

标点那轮的执行者做得很对：工作区当时有 8 个红（对方的中间态），
它**把对方的文件回滚到 HEAD 做了一份隔离副本**，证明
「HEAD + 只有我的改动 = 0 failed」，再逐个 grep 确认那 8 个失败
没有一个引用它的代码。**这是并行作业里最该有的自证方式。**

### 一个意外收获
两次 503 中断反而帮了忙。如果那个 agent 一路跑完，它会交付一个
**看起来完全达标**的 ①（预热 840ms → 0.9ms、测试全绿——因为它正打算去改
那两个失败的测试）。而里面藏着一个我任务书没覆盖的耦合：
**混合简拼从此依赖 `abbrev.bin` 存在**，而 `lookup_mixed` 的文档注释还写着
「副索引缺失不影响本查询」——注释和行为已经不一致。

是那个失败的测试（`real_abbrev_mixed_lookup` 用 `MmapDict::open()` 不挂副索引）
把耦合顶出来的。**这就是为什么不许改测试凑绿。**

## ⑲ 长串打错也能用:分段上屏 + 容错解码 + 剩余串出路(2026-10-02/03)

三期一起交付(`e43093c` 分段上屏、`40e1297` 容错解码,以及同一轮的收尾)。
验收口径与数据都留在 `examples/regression_probe.rs` 的两次输出里:基线
`/tmp/xwx_phase0_baseline.txt` 对拍 `/tmp/` 下的各期结果。

### ① 分段上屏(`e43093c`)

候选带 `Candidate.covered`(覆盖输入串开头的字节数;`0` = 未知/整串,是
字段引入前的语义,所以旧数据与未标注来源一律按整串消耗,不会退化成
「消耗 0 字节」)。会话层只消耗 `covered` 那段,剩余串留在 preedit 继续出
候选;IBus 层新增 `SessionOutput::CommitSegment`:先 `CommitText` 再刷新
预编辑区/候选窗,**不收起**。刷新失败时把前缀原样放回并返回 Err——

> **不变量:已上屏文本 + 剩余输入串 ≡ 用户敲过的全部字母。**

这是「永不静默丢字母」的可执行形式(`segmented_commits_never_drop_typed_letters`),
也修掉了改动前「选一段、后面全丢」的老行为(基线里 `beijin` 选「被禁」后
`preedit_after=""`,连 `jintian` 都丢)。

### ② 容错解码(`40e1297`)

- `segmenter::TypoSyllables`:懒构建「窗口 → ≤1 次编辑可达的规范音节 + 代价」
  索引(四类错误:插入/删除/替换/调换,Cooper 1983;代价 `-log10 P(操作)`,
  混淆概率复用 `corrector.rs` 那张表)。窗口限 2~4 字母、必须含元音、每窗口
  只留最便宜的一条读法。
- 容错格**以精确格为底**:克隆精确格,只在「走不动的位置」附近补弧,且只推
  「用过弧」的新边。
- 门槛两道:整串可精确切且有完整路径 ⇒ 不进容错;已有覆盖整串的读法且分数
  更高 ⇒ 不动它(`nih`/`zhongg` 的真简拼目标词不会被顶掉,`shenem` 的
  「什么」分数更高则照样顶掉「神而明之」)。容错候选进模糊层。

**判据演化(三次试错,都留在这里免得后人重走)**

| 做法 | 结果 |
|---|---|
| 容错弧对每个窗口都开 | 正确长链被垃圾分支饿死:每起点 64 步预算全花在 `wo+me` 这种岔路上,`womenjintianqugongyuann` 里「我们今天」缺席;长串单次 19.6ms |
| 按「第一个不可精确切分的位置」定位错处 | 音节内部的位置、别的切法造成的伪边界都会误判(把错处判到第 4 字节),反而更差 |
| 按**格上可达 + 没有出边**定位(现在的做法) | 与真实打字行为同构,一个输入只有一两个错处位置;质量最好且成本可控 |
| 长串把每起点预算降到 16 | 延迟只降 3~4ms,却饿掉整句读法(「我们今天 #1」→「我们 #1」),**已回退** |
| 容错格重建整张格 | 长串 15ms;改成「克隆精确格 + 补新边」 |
| 容错格上跑 beam 判「有没有走到底」 | **吃掉 10ms**(beam 是 O(位置×桶宽×桶内边数));改成后向 DP 的 `result[0].is_finite()`,语义等价、每条边只碰一次 |

### ③ 剩余串的反馈与出路

- **反馈**:剩余串一直显示在预编辑区(第 ① 期);候选由剩余串重新算出。
- **出路**:候选里没有任何条目覆盖整串时,补一条覆盖整串的**原样上屏**逃生口
  (`echo` 语义:不学词、不动上文,分数压到 `ESCAPE_HATCH_SCORE = -1000` 排在
  真实候选之后)。用户的另外两条路早就有:**Enter** = 拼音串原样上屏、
  **Esc** = 丢弃当前输入。

## ⑳ 延迟收口:混合简拼层的三处扫描 + 一处不确定性(2026-10-03)

第 ② 期验收时发现「单次 <5ms」没达标,而且**基线本来就没达标**——`jintian`
(7 个字母的普通词!)单次 6.70ms。剖析结果出乎意料:建格 0.13ms、beam 0.25ms、
候选打分 0.09ms,真正的大头是**混合简拼层** `lookup_mixed` 5.5ms。

### 三处纯性能优化(输出逐字节不变,对拍已验证)

1. **`lookup_mixed_full_pinyin` 的前缀区间扫描**(主因,`jintian` 5.01 →
   0.15ms)。原实现对每条切分都从 `lower_bound(prefix)` 起扫到前缀区域结束,
   而:
   - `tail` 为空时(整串就是这条切分),整个区间里**唯一会被收下的 key
     就是恰好等于 prefix 的那一条**,其余都被 `if tail.is_empty()
     { continue; }` 丢掉 ⇒ 改成一次二分直达;
   - `tail` 非空时,收下的 key 必须形如 `prefix + ' ' + <后续音节>` 且后续
     音节**首字节等于 tail 首字节**(第 908-913 行的判据)⇒ 扫描区间直接
     从 `prefix + ' ' + tail[0]` 起,并用它做 break 条件(原来用 `pb` 做
     break,会把「ji o*」「ji x*」整段扫完再退,每条都只会被丢掉)。
   - **踩过的坑**:第一版顺手把 `rest` 也改成从 `nb` 之后起算,结果判据
     `rest_syls[0][0] == tb[0]` 拿被吃掉首字母的音节的第二个字母去比,
     `ren` 的 `re n*` 一读少了 94 条(总量 113 → 19)。对拍 oracle 当场抓到,
     测试 `abbrev_quota_is_floor_not_cap` 变红。`nb` 只许参与区间,不许
     参与判据。
2. **`MixedDfs::dfs` 的字面音节分支按首字母分桶**(`zhongguor` 5.76 →
   1.83ms)。`syllable_matches` 要求 `rest[..syl.len()] == syl`(或 üe 归一后
   相等),**首字节不同的音节永远不可能匹配**,而原实现每个节点都要把整张
   音节表(~410 条)试一遍。分桶后每节点只试同首字母的十几条;桶内保持
   长度降序 ⇒ 匹配顺序、收集顺序、`MAX_MIXED_COLLECT` 截断点全部不变。
   非小写字母起点回落整表(行为不变)。
3. 顺带把 `dict.rs` 两处收尾排序改成**全序**:`freq 降序 → 词 → 全拼`。

### 一处**不确定性**发现(比性能更要紧)

做对拍时发现:**同一个二进制,两次运行候选顺序会不同**——`sh` 第 28 名
「谁」的拼音在 `shei`/`shui` 之间跳、`zh` 的简拼层整段尾序不一致。根因是
`lookup_mixed` / `lookup_mixed_full_pinyin` 从 `HashMap` 迭代出来直接
`sort_by_key(Reverse(freq))`,**同频词之间没有全序**,于是继承了 HashMap
的每进程随机迭代顺序。

已修:`dict.rs` 两处排序补上 `词 → 全拼` 收尾键(实测 `zh` 从随机变为确定)。
**残留**:`sh`(2 字母、打字中)仍会跳 —— 它的并列发生在 `lib.rs` 更上层
的合并路径上,尚未定位到具体那一步;影响面是「同频同分、仅拼音写法不同的
同一个字」的名次,用户可见的是 `谁` 的注音字段。**对拍工具读结论时要按
「同频并列忽略」处理**,别把这类差异当成退化。

### 结果(真实词库 release,`min_ms` = 30 次取最小)

| 输入 | 基线 | 优化前 | 优化后 |
|---|---|---|---|
| `jintian`(普通词) | 6.70 | 6.63 | **1.87** |
| `zhongguor` | 5.56 | 5.71 | **1.88** |
| `xian` | 3.52 | 3.51 | **0.94** |
| `zgr` | 1.23 | 1.24 | **0.75** |
| `zhongg` | 3.42 | 3.22 | 3.73 |
| 最大(病态长串) | 8.90 | 10.21 | **6.59** |

### ⚠ 修回两个被静默丢掉的胜例(oracle 的盲区)

第 ② 期收尾时,`shenem → 什么 #1` 和 `womenjinxtianqugongyuan → 我们今天 #1`
两个胜例**悄悄退回了基线行为**,而且躲过了当时的对拍检查——因为对拍只比
「列表有没有变化」:**退回基线 = 没有变化**,于是最坏的一种退化正好是盲区。

根因是容错格「克隆精确格 + 只补新边」时的**链起点范围**搞错了:
`shenem` 的「什么」需要 `[shen][me]` 这条**从 0 起、止于 6** 的整链边
(`em`→`me` 的调换弧覆盖错处 5)。当时把重新枚举的起点限制在
`stall − MAX_TYPO_WINDOW` 之后(想省成本),起点 0 被排除,这条边永远
生成不出来,「什么」整条消失。

- 修:**从 0 枚举到最深错处**(错处之后的部分由弧沿链走完,不需单独当起点),
  并且**每个起点只枚举一次**(不再对每个错处各来一遍,长串开销从 5 份降到 1 份)。
- 教训:对拍判据必须**点名目标词**(「`shenem` 第 1 名必须是『什么』」),
  不能只看 diff——退回基线在 diff 上是隐形的。
- 教训二:我一度按「最深错处才是真错处」把所有错处压成一个来提速,
  结果 `womenjinxtianqugongyuan` 的「我们今天」又丢了(它靠的是覆盖
  位置 4/7 的弧,不是最深的 8)。**已回退**,`first_stalls` 的全部位置都保留。

### 确定性补完 + 一处重复计算(2026-10-03)

- **候选顺序现在完全可复现**:`lib.rs` 里还有**四处** `HashMap` 直接

## ㉑ 分段上屏改成「确认段留在组合里」(方案 b,2026-10-03)

**起因(用户报的交互问题)**:一长串拼音里选了一段之后,按退格键删的是**剩余串
的末位字母**,而用户的心智模型是「回退到上一步重新选」。根因是第 ① 期把选中的
段立刻 `CommitText` 交给应用了——交出去就收不回来,退格除了删字符没别的可做。

**改法**:选中的段不再立刻交给应用,而是进 `InputSession.confirmed`(确认段栈),
预编辑区显示 = **确认段文本 + 剩余拼音串**;整个组合结束时才**一次** `CommitText`。

- `SessionOutput::CommitSegment` 变体**删除**——不再需要「上屏一段还留着组合」
  这种语义;确认段走 `Updated`(只刷新界面),`xwx_ibus` 侧的对应分支一并删掉。
- 触发撤回不了的问题自然消失;`append_to_commit` 只剩 `Commit` 一条分支。
- **退格规则**(按用户口径):只要还有已确认段,退格就**回退上一次确认**——把那段
  消耗掉的字母原样还回输入串、重新出候选,**不看光标位置**。选完一段后光标落在
  剩余串末尾(用户还在继续打字),若要求「光标在分界处才回退」,用户就得先把剩余
  串一个字一个字删光——那正是要修掉的手感。全部退回之后才回到文本编辑惯例。
- **记账(造词缓冲 / 上屏尾部 / UserLM)推迟到组合结束**(`replay_confirmed`):
  中途确认的段还没交给应用,用户随时能退回来——若在确认当时就写 UserLM,回退
  就得做「反学习」。
- 结束路径统一:整串候选被选中 / 回车 / 标点 / Verbatim 字符 / 切英文 / 只剩确认
  段时空格 —— 都走 `commit_selection`(确认段 + 这一条)或 `finish_with_raw`
  (确认段 + 原样字母),**一次**交给应用。
- **边界状态**:剩余串可能被退格删空而确认段还在(`composing()` = 两者任一非空)。
  这个状态下回车/空格/Esc/退格都必须按「组合仍在」处理,否则用户选过的段既上不了
  屏、也退不回来——四个分支的守卫都从 `!pinyin.is_empty()` 改成 `self.composing()`。
- **焦点切换**:`reset_for_focus_change()` 现在返回「已确认但还没交给应用」的文本,
  `xwx_ibus` 的 `reset_state` 补一次 `CommitText`——用户明确选过的内容不能因为切
  窗口就丢。未确认的剩余字母仍按原有语义丢弃(那是「还没选」的内容)。

**行为变化清单(换会话接手时需要知道)**
1. 选中的段不再立刻落进应用,整串结束时才落(一次 `CommitText`,不是多次)。
2. 退格:有确认段 → 先回退选择;没有确认段 → 照旧删光标前一个字符。
3. Esc 丢弃**整个**组合(含已确认段)——它是「取消这次输入」,与主流输入法一致。
4. 标点/回车/切英文会把整个组合一次上屏,且标点拼在末尾。

**验收**:`just verify` 全绿(247 单元 + 49 集成等,clippy `-D warnings`);
A 段(候选列表)与改动前**逐字节相同**——这次只改会话/IBus 的交接时机,没碰解码与排序;
新增单测 3 条(确认段留组合 + 退格回退 + 结束时一次上屏),D-Bus 集成测试
`selecting_a_prefix_candidate_keeps_the_remaining_pinyin_composing` 按新语义重写
(确认时零 `CommitText`、退格还回字母、结束时一次提交 `你好北京`)。

## ㉒ 「一字一字母」收严:`yij` 不再出「已经是」+ 补全读法回到精确层(2026-10-02)

用户报的两条(「`yij` 会出现『已经是』」「简拼排序像没排序,全拼很好」)查下来是
**同一条规则的两个面**:判据只看字数,层序把补全读法当成了缩写。

### 一、`yij` → 已经是:只挡了「字数 > 字母数」

`MixedDfs::collect` 的「一字一字母」原先比的是「候选字数 ≤ 输入字母数」,
于是 `yij`(3 字母)配 key `yi jing shi`(3 字)刚好放行——而这个 key 里「是」
那个音节**一个字母都没打**(`yij` = `yi` + `j(ing)`,`shi` 是字节前缀扫进来的)。
实测它在简拼池里按词频排第 12/500,平时被 `ABBREV_QUOTA=5` 截住;换
`yijs`/`yijshi`/`yjshi`/`yijingshi` 它就是第 1~2 名——症状随时会冒出来。

> **判据改成**:`mid_syllable` 时,key 在前缀之后**不许再有空格**(= 不许再起音节)。
> 等价口径:**每个字至少对应一个打字字母**。

### 二、补全读法被当成缩写读法:`beijin` 的北京排在 #35

排序键的第二键是层序(Exact → Fuzzy → Abbrev),而「末尾半个音节」补全
(`beijin` → `bei jing`)原先也标 `Abbrev` ⇒ 它排在**所有**精确候选之后:

| 输入 | 目标词 | 前 | 后 |
|---|---|---|---|
| `beijin` | 北京 | **#35** | **#1** |
| `niha` | 你好 | **#26** | **#2** |
| `meiyo` | 没有 | **#32** | **#1** |
| `zhongguor` | 中国 | #80 | **#4** |

第一页原先全是只覆盖前缀的单字(`beijin` 前 10 = 被禁/北进/被/备/北/背/呗/杯/辈/悲)。

> **修法**:`lookup_mixed` 把 T2(末尾半音节)那一轮**单独收池**、标 `Exact`
> ——它的读法本来就是「输入是候选拼音的精确前缀,只是最后一个音节还没打完」,
> 与格子里「打字中的补全词」(`zhon` 时的「中」)同类;交错 DFS / 全拼路的候选
> 仍是 `Abbrev`(末位音节只给首字母)。`abbrev_candidates` 不再统一覆盖 `spelling`。
>
> **为什么不干脆「分数先于层序」**(已试、否决):那会把 `beijing` 的低频缩写词
> 「被禁锢」(freq=100)抬到 **#5**——层序键本来就是挡这类词的。只把**补全**读法
> 挪进精确层,两个症状一起好,缩写层照旧被层序挡着:同一版实测 `beijing` 前 10
> 与改动前逐条相同,被禁锢落 **#37**;`diannao` 的狄安娜仍 #11(既有标定不破)。
