# RecallHit：把「召回事实」与「展示候选」分开

A2 的目标结构。**当前状态：设计定稿，未实现**（看板卡 `t-mur20d0m-kvtj99`）。

## 为什么要这一层

候选从四条互不相干的路径产生，各自带着不同的「事实」，现在这些事实只能靠
`Candidate` 的 `spelling`、`covered`、`pinyin` 三个字段间接表达，于是出现四个
结构性缺陷（括号里是本仓库的实证）：

| 事实 | 现在怎么表达 | 出问题的地方 |
|---|---|---|
| 来源 | `spelling` 一层 | 简拼层里混进 `Exact` 补全 ⇒ 白占简拼配额（已修：按拼写分层） |
| 拼写类型 | 同上 | 缩写读法与前缀读法共用同一标签 ⇒ 前缀读法被当成覆盖整串（**未修**） |
| 消费范围 | `covered` | 排序首键不看它（只看拼写标签）、去重键不含它 |
| 编辑数 | 只在边上 | 容错层没有保底名额时会被整表截断（已修：统一配额） |

关键教训（两次实测得出）：
1. **放宽去重键不是修法**——把 `(word, pinyin)` 加宽成 `(word, pinyin, covered)`
   后，v1 对拍 310 行、**重复 word 从 4 条涨到 10 条**（用户会看到同一个词出现两次）。
   内部要共存，**展示仍要折叠**。
2. **改排序首键要看得到效果**——把简拼层的前缀读法从 0 桶改成按实际覆盖查表后，
   44 条语料 **0 行差异**：说明要么这个情形在真实输入里罕见，要么它被别的键挡住了。
   在找到**会显形**的输入之前，不要动它。

## 结构

```rust
/// 一条召回事实：谁、以什么拼写、消费了输入的多长一段、花了几次编辑。
struct RecallHit {
    source: RecallSource,   // Lattice | Abbrev | Tolerant | Sentence
    spelling: SpellingKind, // Exact | Fuzzy | Abbrev（沿用现有枚举）
    consumed: usize,        // 消费的输入字节数（干净串坐标）= 现在的 covered
    edits: u8,              // 该路径上的编辑次数
}
```

## 三条流水线

1. **收集**：四条路径各自产出 `(RecallHit, Candidate)`，**不去重**——同词同音不同
   `consumed` 是两条事实，都要留。
2. **折叠**：按 `(word, pinyin)` 折叠成展示候选，保留**消费范围最大**的那条作为
   该候选的 `covered`（分段上屏要的是「这个词最多能吃掉多少」），同时记下它来自
   哪条 `source`（决定层序与配额归属）。
3. **排序与配额**：层序仍按 `spelling`（精确 → 模糊 → 简拼），但**首键改看折叠后的
   `consumed`**：覆盖整串的进 0 桶，只覆盖前缀的按真实终点查 `umin`；配额按
   `source` 分配（简拼保底、容错保底各自独立）。

## 落地顺序（每步都要旧实现必红的用例 + 四项验收）

1. 纯结构：定义 `RecallHit`，先只在**简拼路径**上产出（不改任何排序/截断），
   断言「同词同音不同 `consumed` 的两条事实都还在」。
2. 折叠：把 `(word, pinyin)` 折叠搬进新层，断言**展示候选里没有重复 word**
   （顺带收掉基线里现有的 4 条重复）。
3. 首键：按折叠后的 `consumed` 改首键，并用并列卡 `t-murt2eic-k3oz8w` 产出的
   输入清单**先找到缺陷 2 会显形的输入**，再动手。
